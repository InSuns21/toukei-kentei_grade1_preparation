# DREAM THEATER 執筆・査読統合規約

このファイルを、`textbook/dream-theater-index.json` に掲載される **DREAM THEATER 数学講座の執筆・改稿・査読における入口となる正本**とする。

目的は、散在していた共通規約・表示規約・演習規約・旧監査台帳の判断基準を一つの順序へ整理し、AI・人間のどちらが編集しても「CI は通ったが教材として薄い」「古い監査記録を現行規約だと誤読した」という状態を防ぐことである。

このファイルは共通規約を全文複製しない。DREAM THEATER 固有の完成条件と、複数の正本をどう合成するかを定める。

## 1. 適用範囲と規約の読み順

対象 `index.md` が `textbook/dream-theater-index.json` に掲載される場合、この規約を適用する。

作業前に少なくとも次を確認する。

1. `CONTENT_GUIDELINES.md`
2. `EXERCISE_GUIDELINES.md`
3. `textbook/style-guide.md`
4. **本ファイル `textbook/DREAM_THEATER_AUTHORING_STANDARD.md`**
5. `textbook/DREAM_THEATER_EXERCISE_POLICY.md`
6. `textbook/formal-statement-presentation-guide.md`
7. `textbook/proof-presentation-guide.md`
8. 対象章の `chapter.yaml`
9. `textbook/knowledge-dag.yaml`、`textbook/dependency-graph.md`、対象系列のカリキュラム・設計台帳

適用範囲が重なる場合は、共通正本 → DREAM THEATER 統合規約 → DREAM THEATER 専用差分 → formal/proof 表示正本 → 個別章設計、の順で解釈する。

用語・一般記号・分布記法・KaTeX・formal statement・proof marker など、より専門の正本がある事項はその専門正本に従う。

PYNUM1 または NUMLAB0–NUMLAB5 を編集する場合は、上記に加えて **`textbook/NUMERICAL_LAB_AUTHORING_STANDARD.md`** を必ず読む。数値ラボの穴埋め演習形式、模範解答、自動判定、theory/lab 台帳、free mode の例外範囲は同ファイルを専門正本とする。

### 1.1 旧監査Markdownを規約として使わない

過去の `f0-dream-theater-*-audit.md` は、特定時点の状態・残件・一時的判定を記録した監査台帳だった。そこに含まれていた再利用価値のある原則は本ファイルへ統合し、旧監査Markdown自体は削除する。

過去状態を確認する必要がある場合は Git 履歴を参照する。古い監査値を現行規約として復活させない。

特に、旧監査にあった **A2/B3** や **全問「問題・詳細解答・本番答案・採点基準」の4区分**は、DREAM THEATER の現行執筆規約ではない。現在は `DREAM_THEATER_EXERCISE_POLICY.md` の **A4/B3/C1** と **詳細解答必須・本番答案/採点基準不要**を採用する。

## 2. DREAM THEATER の目的と読者モデル

DREAM THEATER は統計検定1級の本番答案訓練ではなく、数学・確率・統計理論を大学数学の標準的な流れに沿って理解し、後続理論を自力で読めるようにする発展教材である。

したがって、通常の試験対策章にある「大学初年度以上の概念は極力避ける」という運用を機械的に適用しない。

**何を既知としてよいかは対象章の `prerequisites` と knowledge DAG で決める。**

- prerequisite にない概念を暗黙に先取りしない。
- prerequisite で既習なら、高度な語でも再定義を機械的に要求しない。
- prerequisite に含まれる概念・定理を知っていることと、その応用を複数段まとめて暗算・脳内補完できることは別である。後者を読者へ要求しない。
- その分野を初めて体系的に学ぶ読者は、専門家が当然視する典型変形・標準的な見方・座標表示・添字操作をまだ持っていないものとして扱う。特に代数・位相・微分幾何・関数解析などでは、分野固有の「見れば分かる」を前提にしない。
- その章で新しく主役になる概念は、意味・定義・例から導入する。
- 後続章の定理を現在章の証明へ逆輸入して循環依存を作らない。

標準数学コアでは「統計に直接必要か」だけで削らず、数学科の標準教科書で中核となる事項を、依存関係の範囲内で体系的に扱う。

## 3. 完成条件

次のいずれかだけでは完成扱いしない。

- `implemented` / `existing-anchor` / `reviewed` 等の metadata
- formal statement が存在する
- proof block が存在する
- 演習数の自己申告値が埋まっている
- CI が green

完成とは、**独習者が prerequisites だけを既知として、本文から主要概念・主要定理・核心論証を追い、演習で自力再現できる状態**をいう。

人手査読では最低限、次を確認する。

1. 定義の意味が本文から分かる。
2. 主役となる定義に、条件を実際に検証する具体例がある。
3. 主要定理について「何を言うか・なぜ欲しいか・どの仮定が働くか」が分かる。
4. 後続依存の主要結果は、本文または canonical dependency で核心証明まで閉じている。
5. 「明らか」「同様」「既知」「標準的」で核心論証を飛ばしていない。
6. learning objective が定理名・見出しだけでなく本文・例・演習のいずれかで実質的に扱われている。
7. 詳細解答を読めば、学習者が紙上で計算・導出・証明を再現できる。
8. 完全証明を閉じた状態でも、定理の意味・動機・最小例・重要な仮定・使い道を追える。

CI green は必要条件であって十分条件ではない。

## 4. 本文の標準学習サイクル

証明を持つ主要論点は、原則として次の学習サイクルを作る。

```text
何が問題か / なぜ必要か
  ↓
最小の具体例・反例
  ↓
定義・定理
  ↓
証明の見取り図・核心
  ↓
完全証明（折りたたみ）
  ↓
何が分かったか / どこで使うか
  ↓
その場で使う具体例・演習
```

見出し名を機械的に統一する必要はない。重要なのは、一般論・定義・定理・証明だけが連続する辞書形式にしないことである。

### 4.1 本文品質

- 新しいモデル固有の記号・対象集合・パラメータを、意味の説明なしに数式だけで導入しない。初出では「何を表す量か」「なぜこの対象を考えるか」を通常文で説明し、可能なら低次元の具体例を一度読ませてから一般形へ進む。例えば経済学なら、$x_i$ が財の量、$p_i$ が単位価格、$p\cdot x$ が総支出であることを説明せずに $x\in\mathbb R_+^L$、$p\in\mathbb R_{++}^L$ だけを置かない。
- 抽象概念では、有限集合・低次元・具体的な関数・列・行列・確率変数など、手で確認できる最小例を優先する。
- 定理の前後に、その意味・必要性・後続での使い道を説明する。
- 「証明したから説明も済んだ」と扱わない。
- 厳密性のために不要な最大一般性を持ち込まない一方、必要な仮定を削って偽の一般性を作らない。
- 本文を短くするために核心論証を削らない。
- 「定理より」「したがって」「同様に」「計算すると」の直後に完成式を置く場合、その間に何が起きたかを読者が prerequisite だけから紙上で再現できるか確認する。対象の取り直し、変数変換、連鎖律、基底表示、添字展開、極限・積分・微分の交換などが複数段あるなら主要中間式を示す。
- 定理や公式を適用するときは、必要に応じて「何に適用するか」「展開点・評価点・次数・方向・基底・パラメータをどう選ぶか」「何を代入するか」を明示する。引用元の定理と結論式の形が大きく異なる場合ほど、この対応を省略しない。
- 章・ページの分割は `CONTENT_GUIDELINES.md` 5.2 に従い、学習者から見た中心問いと学習サイクルで決める。migration source、canonical owner、旧ページの境界、実装 phase を章境界として持ち込まない。
- **DREAM THEATER 各章の公開タイトルは、その章の `index.md` の H1 を正本とする。** H1 は原則として「章ID + 学習者向けの内容名」とし、科目見出しで既に分かる情報を `標準実解析 VI：`、`標準位相 III：` のように重ねて持たせない。系列内の通し番号や制作上の区分ではなく、そのページで何を学ぶかが直接分かる題名を優先する。
- H1 を変更したときは、同じ章の `chapter.yaml.title` も内容名へ同期する。stable ID・anchor・ディレクトリ名は、表示名を整える目的だけでは変更しない。
- 公開 `textbook/dream-theater.md` の章リンク表示名と DREAM THEATER 専用サイドバーは、Pages 組み立て時にリンク先 H1 から生成する。したがって索引側に章タイトルの第二正本を作らない。索引の分類・順序・リンク先は `dream-theater-index.json` と `dream-theater.md` が担い、章名そのものはリンク先 H1 が担う。
- 同一ページに独立した中心問いが複数あり、それぞれ別の「定義→定理→証明→演習」サイクルを形成するなら分割を検討する。
- 反対に、前提知識が共通で一続きの理論を構成する隣接内容は、細かい別章を増やす前に節・小節としてまとめられないか確認する。
- ページ長・文字数だけでは分割しない。一つの中心定理を最後まで構成するために長い場合は一講義としてよい。
- 学習者向け本文・章頭・目次には、`CONTENT_GUIDELINES.md` 5.1 に定める編集履歴・管理語彙を置かない。「この章の停止線」のような編集ラベルも使わず、必要な範囲説明は通常の学習案内として書く。
- 公開導入ページ `textbook/dream-theater.md` は、DREAM THEATER 全体の短い序文・読み方と科目索引から構成する。索引部分は `DREAM THEATER 本編` の下を **基礎科目 → 解析系 → 計算系 → 幾何系 → 代数系 → 応用系** の大分類で並べ、その下に実解析・線形代数・確率論などの科目見出しを置く。Encore・外伝・関連科目・計算数理など制作経緯由来の系列名で章立てしない。
- `textbook/dream-theater.md` の冒頭には、DREAM THEATER 全体の目的・読み方を伝える短い序文・オリエンテーションを置いてよい。一方、各科目見出しの直下には紹介文・前置き文を置かず、科目見出しから章リンクへ直接つなぐ。ODE・Fourier解析・PDE、確率解析・時系列、数値解析・差分法・有限要素法・Monte Carlo・準 Monte Carlo のように複数科目を束ねた系列は、公開索引では科目ごとに分ける。
- `textbook/dream-theater-standard-math-core.md` は学習者向けの読む順ガイドとする。数学的な依存関係の正本をこのページ自身や別の中央カリキュラム YAML に重複保持せず、各章の `chapter.yaml` / `knowledge.yaml` の prerequisite と、各 `knowledge.yaml` の概念 `requires` を基に読む順を決める。原則として科目を章単位に細切れにせず、長大系列または科目間依存のため必要な場合だけ、内容上自然な一学期相当の境界で I / II に分ける。章別の実装状況・実装順・`core / bridge / advanced-standard` の区分・旧章との役割分担などは公開ページへ載せない。

### 4.1.1 図・SVG の利用と査読

数学図のAI生成・修正時の作図手順、外部資料に基づく品質基準、構造lintと人手査読の分担は [DREAM_THEATER_SVG_QUALITY_GUIDE.md](DREAM_THEATER_SVG_QUALITY_GUIDE.md) を参照する。数学的な意味を図で確定し、生成・機械検査・実レンダリング・再計算・修正を反復する。機械検査が合格しても視覚・数理査読を省略しない。

図は装飾ではなく、本文だけでは見落としやすい構造・向き・対応関係を読者が確認するために使う。幾何配置、座標系、ベクトルの向き、可換図式、グラフ、物理的な自由物体図など、**空間的・関係的な情報を文章と式だけで追う負担が大きい場面**では図の追加を積極的に検討する。一方、本文と同じ情報を見栄えのためだけに重複させる図は増やさない。

線図・模式図・グラフなどは、拡大しても劣化せず数式教材との相性がよい **SVG を第一候補**としてよい。ただし写真・連続階調画像など SVG が不自然な対象まで強制しない。

図を追加・変更した場合、人手査読では少なくとも次を確認する。

1. **学習目的**：その図が何を見せるためのものかを本文から説明できる。図を消すと理解が難しくなる情報があるか、または誤解を防ぐ役割がある。
2. **本文・数式との一致**：図中の記号、添字、向き、座標軸、領域、境界、符号、単位が本文・formal statement・演習と矛盾しない。
3. **対象・始点・作用点**：ベクトル、写像、力、速度、加速度、法線、接線、経路などは、どの対象に属し、どこを始点・作用点として、どちらへ向くかが曖昧でないようにする。物理図では「どの物体に働く力か」だけでなく作用位置も確認する。一様重力場で剛体を描くなら重力の合力は重心から、接触力は接触領域から描く。接触力が面に分布する場合は、分布を描くか、その合力と作用線を明示する。速度・加速度を軌道上の点へ付ける場合は、その点を始点とする。見やすさのため別位置へ平行移動した補助矢印は、実ベクトルと誤認されないよう「方向のみ」等と明記する。
4. **座標・符号規約**：正方向、原点、角度の向き、基準点、必要な単位を図または直前の本文で確定する。符号規約を図だけに隠さない。
5. **グラフの意味**：関数・数値結果のグラフでは、軸が何を表すか、必要な範囲・尺度・単位、重要点や曲線の意味が分かる。見た目を整えるために定性的形状を偽らない。
6. **可読性と衝突回避**：通常の本文幅とスマートフォン相当の縮小表示で、主要ラベル・矢印・線種が判別できる。文字を矢印・軌道・座標軸・図形の輪郭の上へ不用意に重ねない。ラベルは対象から離しすぎず、どの線・点・ベクトルを指すかが一目で追える距離に置く一方、文字と対象線が接触・重複しない余白を確保する。独立した二つの矢印や曲線を、色だけを変えて同一線分へ完全に重ねない。まずは同一図のまま、ラベル位置、余白、短い引出線・補助線、角度弧、線種、線幅、作用線、分布力表示などを調整して衝突を解消する。物理的に不正確な横ずらしでごまかさない。数学的・物理的に意味のある交点・共通端点は許容するが、交差や重なりが別の関係を誤読させない配置にする。細すぎる線、過密な注記、極端に小さい文字も避ける。
7. **図の一体性と分割の最小化**：同じ現象・同じ座標系・同じ幾何配置を説明する情報は、原則として一つの図の中で関係が読めるようにする。パネル分割や別図化は、上記の配置調整・補助線・線種変更等を試しても、(a) 物理的に正しい位置関係を保てない、(b) 必要なラベル衝突を避けられない、(c) 一枚では過密になり対応関係を誤読する、のいずれかが残る場合に限る。分割した場合は「なぜ一枚では不適切だったか」を査読で説明できるようにする。単に作図しやすい、色分けしやすい、lint を通しやすいという理由だけで分割しない。
8. **配色と色への非依存**：モノクロ固定は要求しない。複数のベクトル・基準系・曲線などの識別を速める場合は、高コントラストの限定色（目安 2〜4 色）を使ってよい。ただし、**比較対象どうしを色だけで区別しない**。同じ図・同じパネルで複数系列を比較する場合は、ラベルに加えて、線種、線幅、矢印形状、始点・終点などの非色手掛かりを少なくとも一つ持たせ、白黒化しても対応を追えるようにする。とくに同じ線種・同じ太さ・同じ矢印形状の系列を色だけ変えて並べる構成は禁止する。装飾目的の多色化や、同一図内で意味が一貫しない配色は避ける。
9. **図中文字の最小化**：SVG 内の可視テキストは、座標軸名、点名、変数・ベクトル記号、角度記号、短い局所ラベルなど、**その位置に置くこと自体が意味を持つ文字**を中心とする。図の目的説明、凡例文、結論、条件、長い補足、「〜は〜方向」のような文章は原則として図の前後の Markdown 本文・キャプションへ置く。可視テキストを画像化して再掲しない。タイトルやアクセシビリティ用説明は `<title>` / `<desc>` に置き、画面上へ重ねる必要はない。
10. **アクセシビリティ**：Markdown 側に内容を表す alt text を付け、SVG 自体にも原則として `<title>` と `<desc>` を置く。説明文は「図があります」ではなく、図が伝える関係を要約する。
11. **本文が正本**：定義、仮定、重要な式、証明の核心を図だけに置かない。図を表示できない環境でも本文を読めば論理が閉じるようにする。
12. **近接説明**：図を本文中で参照し、「何を確認すべきか」を図の前後で短く説明する。画像ファイルだけを置いて読者に意味を推測させない。
13. **編集可能性**：自作図は可能な限りリポジトリ内に原典を保持し、外部ホストだけへ依存しない。章固有図は原則として章ディレクトリ配下の `assets/` に置き、意味の異なる図を同一 SVG の使い回しで済ませない。
14. **数理・物理監査**：図の美観とは独立に、作図された幾何・グラフ・力・軌道・依存関係を本文と同じ厳密さで再計算・再確認する。図が直感的にもっともらしいことを正しさの根拠にしない。
15. **実レンダリング確認**：SVG を追加・変更した場合は、ソースコードだけを読んで査読完了としない。実際にレンダリングし、少なくとも通常表示と本文幅を縮めた表示の両方で、(a) 文字と線・矢印の衝突、(b) 矢印の始点・終点と作用点、(c) marker や文字の切れ、(d) z-order による隠れ、(e) viewBox 外へのはみ出し、(f) 色を失っても残る識別手段を目視確認する。変更図が複数ある場合は一覧表示でも相互に比較し、図ごとの配色・線幅・文字サイズが不必要にばらつかないことを確認する。
16. **SVG レイアウト lint**：DREAM THEATER の章内 `assets/*.svg` を新規追加または変更する場合、ルート `<svg>` に `data-layout-lint="strict"` を付け、`npm run validate:svg-layout:changed` および `npm run validate:svg-quality:changed` の対象とする。strict 図では、文字の推定バウンディングボックスが線分・図形境界・対応可能な path と交差したら blocking error とする。また同じパネルで比較する系列には `data-series-group` / `data-series-label` を付け、同一グループの異なる系列が色以外では同じ線種・線幅しか持たない場合も blocking error とする。自動検査は目視確認の代替ではなく、単純な重なりと色だけの系列識別を機械的に防ぐ最低線である。どうしても意味のある交差が必要な場合だけ、該当要素に理由付き `data-layout-ignore="text-overlap: <reason>"` を付けて局所例外化し、図全体を除外しない。

自由物体図、座標変換図、軌道図、位相図、可換図式などが learning objective の理解に直接効く章では、図を置かない判断にも教育的理由があるかを査読時に確認する。ただし「各章最低 N 枚」のような枚数ノルマは設けない。

### 4.2 動機を先に渡す

新しい主要概念・構成・定理は、可能な限り formal statement から始めない。読者が「なぜ今これを導入するのか」を理解できるよう、導入前後で次の筋道を作る。

1. **今まで何ができたか**：既習の道具で扱える範囲を短く確認する。
2. **どこで困るか**：既存の道具では自然に扱えない最小の問題・失敗例・不便を示す。
3. **何をしたいか**：新しい概念が答える問いを通常文で明示する。
4. **何を導入するか**：定義・構成・定理を提示する。
5. **何ができるようになったか**：導入直後に、最小例または後続結果への接続で効用を確認する。

すべての小さな補題に長い歴史説明や物語を付ける必要はない。一方、その科目で初めて現れる主役概念、学習の視点が切り替わる概念、抽象化の段差が大きい概念では、少なくとも「既存手段の限界」と「新しい対象の役割」を省略しない。

特に、定義・定理・命題が数個続いたあとで初めて目的が分かる構成は避ける。読者が formal statement を読む前に、その statement が何の問題に答えるのかを分かる状態を作る。

### 4.3 knowledge DAG 上の初出定義を CI で守る

`knowledge.yaml` の `concepts` にそのページ自身の `kind: definition` として登録した概念は、そのページで新しく導入する概念とみなす。変更された DREAM THEATER ページでは、対応する初出の formal definition より前に、読者向けの通常文による導入が少なくとも一つ存在しなければ changed-only strict validation を失敗させる。

機械検査は文章の教育的十分性を判定しない。確認するのは「定義パネルへ入る前に、数式・見出し・formal statement ではない読者向け説明が存在する」という最低限の構造である。導入文が本当に「既存手段の限界 → 解きたい問い → 新しい概念の役割」を伝えているかは `audit:formalism-pedagogy` と人手査読で判定する。CI を通すためだけの「ここで次の定義を導入します」のような定型文を置かない。

同じ節で密接に関連する複数の定義をまとめて導入する場合は、節頭の一つの導入説明を共有してよい。また第1節の最初の定義は、章頭オリエンテーションが十分な導入を担っていればそれを利用してよい。

教育上の理由で導入文を置かない方が自然な例外は、対象の concept ID と具体的理由を、初出定義より前に次のコメントで明示する。

```md
<!-- definition-intro-skip: concept.id | 既習概念の局所的な記号規約だけを固定するため -->
```

複数 concept を同じ理由で除外する場合は ID をカンマ区切りにしてよい。理由のない skip、対象定義より後の skip、別ページや非 definition concept を指す skip は無効とする。ページ全体を loose にする包括的な除外は設けない。

実装上、この検査は既存の `audit-dream-theater-concepts.mjs --strict --changed-only` に統合する。concept audit がすでに読み込んだ `dream-theater-index.json`、各 `knowledge.yaml`、本文を再利用し、導入検査だけの別ジョブ・別全体走査は追加しない。これにより PR では変更ページだけを blocking 対象とし、CI 時間の増加を小さく保つ。

## 5. 定義・具体例・反例

formal statement の表示・anchor は `formal-statement-presentation-guide.md` に従う。

主要な定義・定理・命題・補題は、ステートメント単体で対象・仮定・結論が分かるようにする。「同じ仮定の下で」「上の関数について」だけで本質条件を外へ預けない。

### 5.1 定義例

定義直後の例は、単に「これは定義を満たす」と宣言して終えない。

直前の定義に複数条件があるなら、少なくとも非自明な条件を式または論理で実際に確認する。主役となる抽象対象ごとに最低1つの直接例を検討する。

例の標準目安は一講義あたり 2〜4 個だが、数を機械的な完成条件にはしない。役割の異なる例を優先する。

### 5.1.1 定義の初出・判定手段・具体例を一続きにする

専門分野の入口や、抽象的な定義から座標・行列・計算による判定へ移る節では、**定義がどこかに存在するだけでは合格としない**。読者が最初にその条件を使う位置で、「何を確かめるのか」「なぜその道具で確かめられるのか」を再構成できるようにする。

1. **使用前の定義確認**：formal statement の見出しだけでなく、その仮定・結論・直前の導入文・定義例に現れる主要専門語を拾い、各語が (a) この章の先行箇所で導入済み、(b) prerequisite から到達できる既出の定義、(c) この位置で初出、のどれかを確定する。(c) は意味・条件・直接例を先に置く。(b) は参照元の実在する定義と適用条件を確認し、根拠として使う箇所で結果名から stable anchor へリンクする。**定義の後段で初めて意味を説明する、同じ形式的定義の別の語にだけリンクする**構成では不十分である。
2. **分野横断の共通概念**：対称・交代など異なる種類の形式に共通する条件（例：双線形形式の非退化性）は、先に既存の線形代数等の共通定義と依存関係を確認する。必要なら適切な先行章へ定義を置いて参照し、分野ごとに異なる定義を無意味に複製しない。一方、双線形形式と複素Hermitian形式、対称性と交代性のように**仮定や数学的意味が異なる概念は同一視しない**。依存の循環や未着手の後続章への依存を作らない。
3. **定義から判定への橋渡し**：定義の確認で行列、座標、固有値、行列式、Jacobian 等を持ち出す前に、「何を表す行列・量か」「どの基底・座標・条件で表示されるか」「元の定義のどの条件と同値か」を明記する。まだ導出されていない同値性が核心なら、基底展開などの必要な中間式を示して説明する。既習の結果がその橋渡しを担うなら、適用条件を確認して使用箇所からその結果へリンクし、不要な重複証明はしない。
4. **条件ごとの直接確認**：具体例で最終行列や答えを宣言するだけで済ませない。元の定義に立ち返り、少なくとも非自明な各条件について「何を確認したか → どう判定したか → なぜ結論できるか」を追う。例えば非退化性と $B(u,u)\ne0$ の全称性は別物であり、行列の可逆性による判定では有限次元等の仮定を確認する。座標を取り替える場合はその変換の可逆性も示す。
5. **査読時の反証テスト**：「定義を初めて読んだ人に、なぜ突然その行列を計算するのか説明できるか」「別の形式でも同じ判定法を使える理由を示せるか」を対象の定義例ごとに問う。内容がつながらなければ本文の説明順・橋渡しを直す。形式的な anchor や CI の成功だけでは通過としない。

この観点は**新規・実質改稿（区分C）では変更章全体、局所数学修正（区分B）では実際の変更箇所と波及する定義・例**に適用する。書式のみ（区分A）をこれだけで全件再査読へ拡大しない。変更章以外の追跡監査は、第10.3節に従い対象章IDの明示依頼時にだけ行う。

### 5.2 反例

仮定が本質なら、可能な範囲で反例・失敗例を置く。

反例では「結論が偽」とだけ書かず、**どの仮定を失い、元の証明のどの機構が壊れたか**まで説明する。

## 6. 証明責務と粒度

証明の表示方法は `proof-presentation-guide.md` に従う。

### 6.1 原則完全証明するもの

次は原則として核心証明を省略しない。

- その章の learning objective そのものとなる主要定理
- 後続章が直接依存する主要結果
- 標準数学コアで、その分野の標準教科書なら証明を学ぶことが自然な結果
- 新しい証明技法・構成法を学ぶための代表結果

証明では必要に応じて、次を局所的に追えるようにする。

- 何を示せばよいか
- 量化順序
- どの仮定をどこで使うか
- 主要な構成
- 各包含・各含意
- well-defined 性
- 存在・一意性
- 極限・積分・微分・和の交換を正当化する条件
- 有限化、閉性、コンパクト性、完備性、可測性などが働く箇所

核心部分を「明らか」「同様に」「標準的議論」「既知」に置き換えない。

また、引用した定理から目的の式までに複数の非自明な操作がある場合、定理名だけを書いて完成式へ飛ばない。たとえば一変数定理を補助関数へ適用するなら、その補助関数、適用区間・展開点・評価点・次数などを示し、定理の式へ代入した中間段階を少なくとも一度書く。線形写像を行列表現するなら、どの基底で何が各列・各成分になるかを示す。

### 6.2 既存正本を再利用する場合

既存の canonical result で証明済みなら、同じ証明を複製しない。

- stable anchor へ直接リンクする。
- 現在の対象がその定理の仮定を満たす理由を局所的に確認する。
- 章トップへのリンクだけで「証明済み」としない。

### 6.3 意図的黒箱

完全証明が別分野の大規模理論・本章の射程を大きく超える理論を必要とする場合だけ、意図的黒箱としてよい。

その場合は、

- この教材では定理として使うこと
- 必要な追加前提
- 証明を扱う正本、または範囲外であること

を読者向けに明示する。

「証明が長い」だけでは黒箱化を正当化しない。

## 7. 演習量と役割

演習数の現行正本は `DREAM_THEATER_EXERCISE_POLICY.md` とする。

新規追加・実質的改稿を行った DREAM THEATER 章は、理由付き例外がなければ実本文上で最低

- Level A: **4題以上**
- Level B: **3題以上**
- Level C: **1題以上**

を満たす。

題数だけ合わせる水増しは禁止する。教育上不自然なら `chapter.yaml` の `dream_theater_exercise_count_exception` に理由を書く。

### 7.1 レベルの役割

- **Level A**: 定義確認、基本計算、証明の一段階など、章の基本操作を単独で実行する。
- **Level B**: 主力。複数の概念・命題を接続し、本文を読んだだけではなく自分で論証を組み立てる。
- **Level C**: 章全体または複数の主要論点を統合する自然な発展問題。単なる計算量増加で難化させない。
- Level D は DREAM THEATER だからという理由だけで院試・研究レベルへ難化させない。

問題数を満たしていても、主要 learning objective を一度も自力使用させていなければ不足と判定する。

## 8. DREAM THEATER の詳細解答

DREAM THEATER では各演習に **詳細解答**を必須とする。

**本番答案・20点採点基準は原則として作成しない。** これは通常の統計検定試験対策章との差分である。

詳細解答は答えの提示ではなく、再現可能な導出を書く。非自明な箇所では必要に応じて、

- 出発点
- 使用する定義・定理
- 適用条件
- 中間式
- 何を代入したか
- どの項が消えるか
- なぜその極限・積分・微分・交換が許されるか
- 結論

を追えるようにする。

「整理すると」「計算すると」「同様に」で複数段の非自明な計算や論証を隠さない。

証明問題では本文の証明を単に複写せず、学習者が証明戦略を再構成できる解説にする。

`EXERCISE_GUIDELINES.md` の途中式・定理適用・問題文自己完結性に関する共通原則は継承する。ただし「本番答案」「採点基準」の要求は `DREAM_THEATER_EXERCISE_POLICY.md` により免除する。

### 8.1 数式をどう配置するか

原則は **短い記号の参照はインライン、計算・導出・判定・結論は独立した別行数式** とする。

- 変数名や短い条件など文章を読むための記号はインライン数式でよい。個数だけで一律に禁止しない。
- 初出の定義、主要公式、二段以上の式変形、証明の決め手、演習の最終結論は原則として別行数式に置く。式を移動するだけで仮定や理由を省略してはいけない。
- 一段落に4個以上のインライン数式が並んだ場合、各式が「短い参照」なのか「独立させて読者に計算を追わせる式」なのかを査読する。特に詳細解答は長い一段落に途中式・判定・結論を詰め込まない。
- 式を別行へ移す際は、日本語の係り受けや読点の残存、式の条件・添字・作用域の欠落、改行による LaTeX の破壊を確認する。既存の formal / proof / solution marker とアンカーを維持する。
- KaTeXの別行表示はドル記号2個の行で囲み、前後に空行を置く。横スクロールや文字の過剰な縮小より、意味のある段階への式の分割を優先する。
- npm run audit:math-layout は過密な段落を査読候補として報告する。機械判定はレイアウトの教育的な適否を保証しない。査読では実本文の式と文章の順序を確認する。スマートフォンの実表示確認は必須としない。
- **二つ以上の条件・要請・設問・行程を番号で列挙する場合は、Markdown の順序付きリスト `1. ...`、`2. ...`、…を使う。** `(1) ... (2) ...` を同一段落に連結しない。formal statement の引用ブロック内では、表示数式が項目間に挟まらないときだけ `> 1. ...`、`> 2. ...` と引用記号を付け、リスト前後に `>` の空行を置く。項目間に `$` 表示数式を挟むと Markdown のリストが切れて後続項目が再び `1.` になるため、**（G1）結合則**、**（G2）単位元**、または定理の各結論に **（1）**、**（2）** のような再採番されない独立ラベルを使い、表示数式は formal panel 内のまま引用記号なしで配置する。番号は 1 から連続させ、列挙前後にかかる条件や結論は箇条書きの外へ分離する。式番号、関数値、文章中の結果番号参照は列挙と混同しない。
- `npm run audit:math-layout -- --changed-only --strict --base <base-sha>` は、新規・変更章の番号連結、引用中の手書き番号、順序付きリストの採番飛びも検出する。変更対象外の既存章は `npm run audit:math-layout` で全体候補として棚卸しする。既存の数学過密段落を保ったままリストのみを直す場合、changed-only strict は新しく発生した過密・採番の問題を blocking とし、旧問題は inventory に記録し続ける。

### 公開ページの直接前提講座リンク

DREAM THEATER の各章の公開ページでは、H1の直下に **「前提講座（直接）」** を表示する。対象は公開索引 `textbook/dream-theater-index.json` に掲載された全章とし、先頭講だけに限定しない。

- **直接1階層**だけを表示し、前提先の前提へ再帰的にたどらない。
- 各章の `chapter.yaml` の `prerequisites` を唯一の正本とし、参照先の `chapter.yaml` の章IDと題名を使ってリンク名を付ける。
- `prerequisites: []` の場合は「なし」と表示する。未解決の章ID・リンク先の欠落は自動検証で検出し、機械的な依存の追加や勝手な代替講座への置き換えは行わない。
- 本文の `index.md` に同じ一覧を重複転記しない。Pages の生成処理が公開MarkdownのH1直下へ差し込む。これにより、章本文の改稿なしに依存関係の更新が反映される。
- `npm run validate:dream-theater-prerequisites` で正本の参照解決とスクリプトの自己テストを行い、`npm run validate:pages` で公開生成後のリンク・配置を再検証する。既存の本文内の個別定理参照や既出概念の説明は引き続き有効である。

### 本文中の既習結果への参照リンク

本文・証明の見取り図・証明・例題・演習の詳細解答で、他章または同章の**既出の定理・命題・補題・定義・公式・構成を論拠として使う**場合、読者がその場から根拠を開けるよう、**適用箇所の結果名に Markdown リンクを付けることを原則とする**。章頭の「前提講座（直接）」表示、prerequisite / knowledge metadata、別の節に置いた既存リンクは、実際に援用する箇所のリンクの代わりにはならない。

- 数式の正当化に使う参照先は、実在を確認した**該当結果の stable anchor**とする。単に章トップへ飛ばすリンクや、見出し名から推測した未検証の anchor で済ませない。リンク先には引用する主張と仮定があるか確認する。
- 特に「○○の定理より」「ODE8の流れの合成則を適用」「前章の補題から」等の**根拠を指す文**を執筆・査読時に洗い出し、使用箇所にリンクを置く。証明の見取り図と証明本文のように別々に読まれる箇所では、それぞれから根拠へ移動できることを優先する。同じ短い段落内で同じ結果を繰り返すだけなら毎回リンクしなくてもよい。
- 単なる復習、比較、学習案内など、特定の結果を論理的に援用していない言及は、文脈に応じて章リンクまたはリンクなしでもよい。文章中のあらゆる数学用語をリンク化しない。
- 記述例：`ODE8の流れの合成則を初期値 $x$ に適用すると` → `[ODE8の流れの合成則](../ODE8/index.md#prop-ode8-flow-law)を初期値 $x$ に適用すると`。
- 同じ章の既出結果を援用する場合も、`[本章の順序保存定理](#thm-cdyn1-order)` のようにページ内の実在する結果アンカーを指す。
- リンクの**URL解決**は Pages link 検証で確認できるが、「必要なリンクが欠けているか」の意味判断は機械的なキーワード一致では網羅できない。大量の誤検出を生む blanket CI を代用にせず、主要証明・演習解答の引用元を人手で突き合わせる。抽出ツールを使う場合も候補提示にとどめる。

### 本文と前提講座の横断照合

公開ページの「前提講座（直接）」は `chapter.yaml` から生成するため、**メタデータに書かれていない実質的前提は自動表示されない**。章の改稿・監査では本文中の既習主張、定理・構成の援用、全演習と詳細解答にある他章参照を点検し、次を区別する。

1. **直接必要な前提**：現在章の主要論証または演習で未証明の定理・定義を使用し、既存 prerequisite の推移閉包からも到達できない。該当する `chapter.yaml` と `knowledge.yaml` の必要な前提を、本文の数学的理由に基づいて修正する。
2. **推移的に既習の前提**：既存 prerequisite を通して導入元へ到達できる。再掲する必要がなければ直接前提を重複させない。
3. **後続参照・比較・学習案内**：導入予定の定理へのリンク、後で使われることの説明、比較・系譜の紹介は、現在章がその定理を証明の入力として使用するわけではない。機械抽出だけで prerequisite へ追加しない。
4. **前提メタデータの差分**：`chapter.yaml` と `knowledge.yaml` の前提が異なる場合は、概念 `requires` と本文の証明・演習を検査する。機械的な集合の一致を目的として循環や未習概念の逆輸入を行わない。

横断抽出には `npm run audit:dream-theater-prose-prerequisites` を使う。変更章については既存の changed-only 概念監査の一部として同検査を実行する。抽出は査読候補であり、概念検証が通ったことや機械抽出結果だけでは真の依存欠落がないとは保証しない。

## 9. 依存関係と重複回避

編集前に対象章の `chapter.yaml` / `knowledge.yaml` の `prerequisites`、概念依存、`dream-theater-standard-math-core.md` の通読順を確認する。通読順は依存関係から導く案内であり、独立した依存DAGの正本として扱わない。

- 未習概念を暗黙に使わない。
- 必要な理論が既存章にある場合、新しい重複 concept・重複定理・重複章を作る前に正本を再利用できないか確認する。
- dependency 追加は CI を通すためではなく、実際の数学的依存がある場合だけ行う。
- 後続理論を証明へ逆輸入しない。
- formal dependency は canonical stable anchor へリンクする。
- 既存章を再利用する場合でも、対象章の learning objective に必要な説明・例・仮定確認まで参照先へ丸投げしない。

### 9.1 `knowledge.yaml` の語彙設計

`knowledge.yaml` の `name`、`aliases`、`introduction_aliases` は役割を分ける。

- `name` は concept を識別する読者向けの主名称とする。
- `aliases` は**同じ概念・定理を指す真の別称**だけに使う。関連語、検索語、構成要素、章内で同時に扱う語、単なる短縮見出しを入れない。
- 一つの見出し・formal label で複数 concept を同時に導入する場合、その見出し文字列は各 concept の `aliases` に重複登録せず、必要な concept の `introduction_aliases` に置く。
- 既出 concept を章内で再掲する場合は、canonical concept を `requires` で参照する。再掲側は「○○の再掲」「この章で使う○○の再掲」のように機械的に一意な名称を持たせ、canonical 名を alias として取り直さない。
- 同じ自然言語が分野ごとに別概念を表す場合、本文の標準語を無理に変えない。global alias は「関数列の下極限」「Markov連鎖の可逆性」「定係数線形ODEの特性多項式」のように必要な文脈を加える。
- stable ID・stable anchor は後方互換性のために保持するが、誤った alias は互換性層として温存しない。alias は semantic resolver の入力であり、URL互換や参照互換の代用品ではない。
- 数学的意味を持つ記号を正規化で落とさない。「弱*位相」と「弱位相」のように `*` が概念識別に効く場合は別 alias として保持する。Markdown の `**` 強調記号だけを装飾として除去する。
- 短い一般語 alias が他分野の concept 名へ広く食い込む場合は、まず「真の別称か」を確認する。真の別称なら WARN を許容できるが、関連語・構成要素なら `introduction_aliases` または本文へ移す。
- concept audit は HTML の tag / attribute、コード、数式、URL など読者本文ではない文字列を概念使用として扱わない。stable anchor の断片が別 concept の alias と一致しても dependency を発生させない。
- 真の別称でも `net`、`unit`、`torus` のように分野横断で多義的な語は `textbook/dream-theater-knowledge.yaml` の contextual alias として扱える。自由文や複合専門語中の部分一致だけでは blocking にせず、formal label、完全一致の強調・リンク文字列・引用など明示的な参照で使用を確定する。
- 「digital net」「単位トーラス」のような標準的な複合専門語が短い alias を含むだけなら、監査を通すために本文語彙を不自然に改名しない。誤検出なら resolver / policy を修正する。

既存 `knowledge.yaml` の alias を変更すると semantic resolution が未変更ページへ波及しうるため、scope detector が full audit を要求する場合は省略しない。WARN をゼロにすること自体を目的に語彙を不自然に改名せず、意味的な誤登録だけを直す。

## 10. 執筆・改稿の作業手順

変更の性質に応じて査読範囲を決める。**新規執筆・数学的な実質変更と、表示だけの変更を同一の全件査読で扱わない。** 以下は規約を読んだという自己申告ではなく、実差分・検算・表示確認に基づく完了ゲートである。

### 10.0 変更区分と査読範囲

| 区分 | 適用対象 | 必須の人手査読・検証 |
| --- | --- | --- |
| **A：表示・書式のみ** | 既存章の空白、改行、Markdownリスト・引用・強調等の表示構造のみ。本文の数学的意味、数式、見出し、anchor、リンク、演習内容、コードを変えない | base と完成版の本文・数式・見出し・anchor・リンク・演習ID・コードの同値検査、実レンダリング確認、changed-onlyと公開・数式関連CI。**主要証明・全解答の数学的再計算は不要** |
| **B：局所的な数学修正** | 特定の定義、証明、例、演習、用語、参照、仮定等を変更し、他の内容を保てるもの | 変更前後の本文と変更箇所を読んで再計算し、直接・間接に依存する主要証明、例、演習解答、定理リンクまで影響範囲を追う。読者粒度・適用条件を再確認。**影響しない部分の全件再計算は不要** |
| **C：新規執筆・実質的改稿** | 新章、新規の主要定理・構成・演習の導入、学修目標や章構成の大きな変更、数学的影響範囲を限定できない改稿 | 従来どおり変更章の全主要証明・全演習と詳細解答を棚卸しし、全件再計算と別観点での再査読を実施 |

- **分類は変更行数やPRタイトルではなく実際の差分と数学的影響で行う。** 複合PRでは章ごとに判定し、不明・境界・確認不能なら上位区分（原則C）へ上げる。PR作成者の「書式のみ」宣言だけではAとしない。
- Aは **既存の章内容が同値** である場合に限る。文字・数式・anchor・見出し・リンク・exercise ID・コードの意味内容を変えた場合はB/C。数式の空白や記号を変えた場合もAとは自動判定しない。構造化Markdownの変換ではリスト番号・引用の表示と式の包含関係をプレビューで検査する。
- Bでは改稿前の実本文、prerequisites、当該の既出結果と使用箇所を確認し、「直接の変更だけ」を根拠なく影響範囲の終端としない。演習問題の変更は対応する詳細解答も再計算する。定義・定理の変更が広域へ波及するならCに上げる。
- Cの新規・変更章自身の査読は維持し、別の完了章の追跡監査は第10.3節の**明示依頼時のみ**とする。
- A/B/Cを問わず、重大な数学的矛盾、表示破綻、リンク欠落、CI不合格を放置して完了扱いにしない。図・SVGを変更した場合の実レンダリング査読は常に必要。

### 10.0.1 区分Cの標準作業手順

1. **対象・前提の確定**：実ファイル、対象章の `chapter.yaml` / `knowledge.yaml`、prerequisite、learning objectives、必要な canonical dependency と本規約を読む。既存章は改稿前の実本文を通読する。
2. **査読対象の棚卸し**：対象章ごとに各 objective、主要定義・主要定理・証明・直接例・全演習ID・全詳細解答を実本文から列挙する。見出しやmetadataと内容の成立を混同しない。
3. **執筆・自己検算**：概念を導入してからformal statementを置き、定理適用・数値例・反例・添字・極限・演習解答の主要中間式を再計算する。
4. **自己査読（全件）**：完成本文を全文再読し、全主要証明と全演習・詳細解答を出発点から紙上で解き直す。「入力 → 適用条件 → 操作 → 中間式 → 結論」を照合し、非自明な2〜4手の省略を補う。
5. **別観点での再査読**：完成本文を初見扱いで読み、prerequisitesのみを既知として定義例・主要証明・全解答の正しさと読者粒度を疑う。同一担当者が再読した場合は「独立第三者査読」と称さず実施形態を記録する。
6. **修正・再査読**：fatal / major / minorを場所・根拠付きで記録し、修正箇所と波及先を再計算する。
7. **検証・最終差分**：変更スコープに合うCIと表示・リンク確認を行い、レビュー記録との一致を確認する。
8. **証拠・完了判定**：第10.1節の区分Cの簡潔な記録を残し、未確認の主要部分があれば未完了とする。

区分Bは上記のうち対象・前提の確認、影響範囲の棚卸し、変更・波及箇所の再計算と別観点の局所確認、修正、検証、記録を行う。変更外の証明・演習を形式的に全件再解答する必要はない。区分Aは最終差分、機械的同値、実レンダリング、CIと記録に集中する。

### 10.1 DREAM THEATER 査読証拠・完了ゲート

PR本文に**区分別の実施概要**を残す。CIは差分と対応する章IDのマーカー、および空欄でない短い査読要約を検査し、**見出しの表記・箇条書きの項目名・全anchor/演習IDの転記は要求しない**。全対象の棚卸しは実本文から行い、PR本文に二重記載しなくてよい。CIは数学的正しさやレンダリングの視認を証明しない。コピー用の簡潔な雛形は [`prompts/dream-theater-review-evidence.md`](prompts/dream-theater-review-evidence.md) を参照する。

- **A：表示・書式のみ**：CIがbaseの本文と完成版の文字列構造を比較し、数式・見出し・anchor・リンク・exercise ID・コード等が保たれると確証できる章にだけ適用する。PR本文に共通 `<!-- DT-FORMAT-REVIEW -->` と、対象章、実表示確認、未解消事項、検証結果を短く記す。複数章を一括で記録してよい。**章ごとの全主要結果・全演習ID棚卸しや数学的再計算は要求しない。** CIがAと確認できない場合はB/Cの査読証拠を要求する。
- **B：局所的な数学修正**：章ごとに `<!-- DT-REVIEW: <章ID> local-math -->` を設け、変更・波及範囲と再計算の具体例、未解消事項、検証結果を短く記す。範囲を限定できない場合はCとする。
- **C：新規執筆・実質的改稿**：章ごとに `<!-- DT-REVIEW: <章ID> -->`（または `substantive`）を設ける。本文では全learning objectives、主要結果、全演習と解答を棚卸しし、全件再計算・別観点再査読を実施する。PR本文には**全件実施の範囲と結果、代表的な主要定理1件・演習1件の仮定・主要中間式・結論、実施主体、未確認事項と検証結果**を簡潔に記す。全anchor・全演習IDの列挙は不要。代表例・CIだけで全件査読に代えない。

**書式と実質を分離する**：CIの記録ゲートはマーカーと短い実施概要があれば通し、定型の11項目への再配置や句読点の違いでは失敗させない。実際の査読の充足・数学的妥当性は作業者とレビュアーが本文・計算・差分から確認する。要約が空欄・テンプレート未記入のPRは通さない。

**gate**：Aの機械的同値・実表示・CIに欠落がある、Bの必要な再計算や波及確認に重大な欠落がある、Cの全件査読が終わらない、またはfatal/majorが残る場合は完了扱いにしない。学習者向け `index.md` へ査読記録を混ぜない。

DREAM THEATER の変更では最低限、変更内容に応じて次を使う。

```bash
npm run validate
npm run validate:pages
npm run validate:dream-theater-exercise-counts
npm run audit:proof-pedagogy
npm run audit:formalism-pedagogy
```

`knowledge.yaml`、全体概念レジストリ、依存監査ロジックを変更した場合は対応するstrict validationを実行する。共通規約・validator・workflowの変更はfull auditとし、通常のleaf変更ではchanged-onlyを優先する。`dream-theater-standard-math-core.md`だけを変更した場合は公開リンク・Pages構築とprerequisiteの整合を確認する。

### 10.2 概念依存監査の範囲

概念依存監査は、変更の影響範囲に応じて使い分ける。PR では変更ページを対象にした changed-only strict validation を通常の blocking 検証とし、すべての教材変更で全 DREAM THEATER を再走査することは要求しない。

次は **changed-only を原則**とする。

- DREAM THEATER 本文・chapter metadata の通常編集
- 新規章の追加
- `dream-theater-index.json` への既存項目を壊さない path の純粋追加
- その新規章に対する新規 `knowledge.yaml` の追加

次は未変更ページへ判定が波及しうるため、PR でも **full audit** の対象とする。

- 既存章の `knowledge.yaml` の変更・削除・移動
- `dream-theater-index.json` における既存 path / section の削除・改名・移動・並べ替え
- `textbook/dream-theater-knowledge.yaml`、`textbook/dream-theater-inference-rules.yaml` の変更
- concept audit の判定ロジック・共通解決ロジック・workflow 自体の変更
- 差分基準を安全に解決できない場合

pure-add 判定は「既存 section と既存 path の順序・所属を保ったまま、新しい section または path だけを挿入した変更」とする。単に index ファイルが変更されたという理由だけで full audit を要求しない。

main への push では全体監査を実行し、リポジトリ全体の drift を継続的に検出する。将来、依存 DAG の downstream closure や alias の逆参照から影響ページを正確に列挙できるようになった場合は、既存章の knowledge 変更についても full audit を impact audit へ段階的に置き換えてよい。

具体的な CI 判定は `scripts/detect-dream-theater-concept-audit-scope.mjs` と `.github/workflows/validate-dream-theater-concepts.yml` を実装上の正本とする。

監査コマンドの警告を、見出しを足すだけで機械的に消さない。本文を読み、実際の欠陥がある場合だけ修正する。

### 10.3 既存完了章の追跡監査（対象IDの明示依頼時のみ）

**この節はユーザーが別の完了章の追跡監査を明示した場合にのみ適用する。** 新章執筆に自動で付随させない。変更章自身の第10・10.1節による区分別査読の義務は変えない。依頼用テンプレートは [`prompts/dream-theater-followup-audit.md`](prompts/dream-theater-followup-audit.md) に置く。

1. **対象確定**：依頼された章IDと GitHub 上の `textbook/dream-theater-series/<ID>.yaml` の `chapters` を照合する。対象章の `chapter.yaml` / `knowledge.yaml` と直接必要な prerequisite を確認する。直前章・別系列の章を推測しない。
2. **実本文の再読と棚卸し**：最新の `index.md` を全文再読し、learning objectives、主要結果・全主要証明、全演習・詳細解答を列挙する。第10・10.1節の変更章査読とは別の追跡監査として記録する。
3. **初出定義と判定例の学習導線**：第5.1.1節に従い、初出の主要専門語と formal statement の仮定を使用位置ごとに洗い出す。既存共通定義の実在・到達可能性、定義より前の使用、定義例で突然現れる行列・座標・判定法の理由と元の条件との同値性、各条件を実際に確かめているかを確認する。既知の定義を形式的に重複させるのではなく、使用箇所のリンクと橋渡し説明を重視する。
4. **数学・行間の再計算**：仮定、定義域、正則性、極限交換、符号、添字、次元、補題の適用条件を検査する。「より」「したがって」「同様」「計算すると」等の後の非自明な2〜4手の飛躍を見逃さない。**指摘0件のときも**飛躍しやすい主要証明2箇所（少なければ全件）と演習解答1箇所を、結論を伏せて出発点から再導出し、具体式と判定理由を記録する。
5. **数式配置とリンク**：第8.1節に沿った別行数式とインライン密度を確認する。`npm run audit:math-layout` は候補抽出にすぎない。本文・見取り図・証明・演習解答で援用する既出結果名から、実在して仮定が一致する canonical stable anchor へのリンクを検査する。
6. **修正と再査読**：fatal / major / minor を位置と根拠付きで記録し、実質的欠陥があれば対象章を修正・再計算する。対象章を変更した場合は第10・10.1節の**変更の性質に応じた査読ゲート**と必要な validation を満たす。ただし追跡監査の全件再計算自体は第10.3節の依頼範囲として省略しない。依頼スコープ外の新章の完了を機械的に妨げない。
7. **証拠と完了判定**：対象ID、主要証明・全解答の棚卸し、代表的な再導出、数式配置とリンクの実例、指摘・修正、未確認事項、実施主体をPR本文または同等の記録に残す。`prompts/dream-theater-review-evidence.md` の任意追跡監査欄を使用できる。未確認の主要部分があれば監査そのものを完了扱いにしない。第三者査読は実施した場合のみそう記す。

追跡監査の着手だけで過去の completed status を差し戻さず、根拠なしに「指摘0件」と結論しない。

## 11. 査読チェックリスト

公開・merge 前に対象章を実際に読み、次を確認する。

### 本文

- [ ] 主要論点に動機または位置付けがある。
- [ ] 新しい主役概念について、「今まで何ができたか → どこで困るか → 何をしたいか → 何を導入するか → 何ができるようになったか」のうち必要な橋渡しが本文にある。
- [ ] 抽象論だけが続かず、手で追える具体例がある。
- [ ] 定義・定理・証明の列だけになっていない。
- [ ] 「〜より」「したがって」から完成式へ飛ぶ箇所で、読者に複数段の非自明な脳内補完を要求していない。
- [ ] 証明を閉じても意味・重要な仮定・使い道が分かる。
- [ ] 旧版・移管・canonical owner・archive・stable anchor・CI/監査など、編集者向けの事情が読者本文へ露出していない。
- [ ] 「停止線」等の編集ラベルや、1リンクだけの過剰な目次見出しを増やしていない。
- [ ] `textbook/dream-theater.md` を変更した場合、冒頭の全体向け序文・読み方の後は「大分類 → 科目 → 章リンク」の構造になり、各科目直下の紹介文や Encore/外伝等の系列見出しが再導入されていない。

### 定義・formal statement

- [ ] formal statement の各主要専門語（見出し・仮定・結論）が初出時点ですでに定義・導入済みか、到達可能な prerequisite の実在する定義へ使用箇所から参照できる。
- [ ] 定義例が行列・座標・固有値・行列式等で判定する場合、その表示が生じる理由と元の定義との対応・必要な仮定が、本文または直接の既習リンクから追える。
- [ ] 主要定義に直接例がある。
- [ ] 定義例で条件を実際に検証している。
- [ ] formal statement が単体で対象・仮定・結論を確定できる。
- [ ] stable anchor があり、論理依存はその anchor へ飛ぶ。

### 証明

- [ ] 主要定理の核心論証を再構成できる。
- [ ] 定理・公式を適用した箇所で、適用対象・パラメータ選択・代入・主要中間式を追える。
- [ ] 既出の定理・命題・補題・定義・公式を実際に援用する箇所には、該当する実在の stable anchor への本文内リンクがある（章頭の前提一覧だけで代用していない）。
- [ ] 仮定を使う場所が局所的に分かる。
- [ ] well-defined 性、存在、一意性、各包含・含意を必要な箇所で省略していない。
- [ ] 「明らか」「同様」「既知」で核心部分を隠していない。
- [ ] intentional black box は理由と境界を明記している。

### 演習・解答

- [ ] 原則 A4/B3/C1 以上、または教育上の理由付き例外がある。
- [ ] 主要 learning objective を演習で自力使用させている。
- [ ] 問題文だけで必要な対象・記号・仮定を特定できる。
- [ ] 詳細解答が紙上で再現可能である。

- [ ] DREAM THEATER に不要な本番答案・採点基準を新規追加していない。

### 依存関係・knowledge metadata

- [ ] prerequisite 外の理論を暗黙使用していない。
- [ ] 後続章を逆輸入していない。
- [ ] 既存正本を再利用できるのに重複定理・重複 concept を作っていない。

## 12. 最終判断原則

規約の形式的充足より、**独習者が数学を再構成できること**を優先する。

ただし「教育的に良さそう」という理由で、既存の正本・依存関係・ユーザーが指定した範囲を勝手に変更しない。

不足を見つけた場合は、その場しのぎの文言・marker・metadata の追加ではなく、実際の欠陥に応じて

- 本文補強
- 具体例・反例追加
- 証明補完
- 演習追加
- 詳細解答補強
- canonical result への参照
- 必要なら章分割

を選ぶ。

**見出し、marker、metadata、CI green を教材完成の代用品にしない。**
