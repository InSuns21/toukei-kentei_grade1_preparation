# FML6 Comparator・独立kernel・再現検証

前提：[FML5 数学的定理の依存関係と公理監査](../FML5/index.md)、[LVT1-02 Lean環境・Lake・再現可能なプロジェクト](../../LVT/LVT1-02/index.md)。

前講では証明が利用する公理を調べました。しかし別の人から証明を受け取ったとき、その人が証明した定理がこちらの求めた定理と一致しているか、また保存された証明を別の検査器でも確認できるか、という問題が残ります。本講では小さな自然数の定理を使って、主張の固定、証明の検査、独立実装での再検査を分けて実行します。

## 1. 問題を出す側と解く側の環境を分ける

前講で学んだ宣言の型と値 の区別を使います。Lean の `Nat` は 0 を含む非負整数型であり、数学の $\mathbb N_0$ に対応します。以下で自然数 n と書くときはこの型の元を指します。まず、すべての n について $0+n=n$ を証明してほしいとします。出題者は Challenge.lean に求める型を記録し、解答者は Solution.lean に同じ名前の定理を証明します。Challenge の sorry は問題を記述するための未完成箇所であり、Solution の証明には使いません。両方を同じ環境へ import すると同じ名前の定義が衝突するため、独立した環境で処理します。

さらに、例えば出題者は step を自然数に1を加える関数と定め、定理 stepRefl の型にその関数を含めます。解答者が step を自然数に2を加える関数へ変更した場合、定理の文字列は同一でも、その定理が参照する数学的対象が変わります。型の印刷結果だけではこの変更を判別できません。ここで `step n` は数学の関数適用 $step(n)$ に対応し、`step` の宣言本体がその値を定めます。

ここで環境とは宣言名から型・定義本体・証明などを参照できる登録情報です。定理のステートメントはその宣言の型であり、参照先の定義も含めて意味が定まります。以下の照合では出題者の定義を未完成のまま解答者に委ねる特殊な課題は扱いません。比較規則は名前・宣言の種類・型の構造と、型から参照する定義等をたどった先の宣言を比較する規則です。対象定理の証明値は比較から外します。

<a id="def-fml6-statement-matching"></a>

<!-- formal-statement-start -->
### 定義（定理ステートメント照合）

出題側と解答側の二つの Lean 環境および比較対象の定理名の有限集合を指定する。各定理名について両環境で宣言が存在し、その型と、型を解釈するために再帰的に参照する定義等の宣言が所定の比較規則で一致することを定理ステートメント照合の条件とする。定理の証明項自体の同一性は要求しない。
<!-- formal-statement-end -->

<!-- definition-example-start: def-fml6-statement-matching -->
**定義の確認**　比較対象を FML6.addZeroLeft と FML6.stepRefl とします。出題側と解答側には両名の宣言があり、前者の型はともに全自然数 n に対する 0 + n = n です。後者の型はともに step n = step n で、step は両環境で Nat から Nat への関数 n ↦ n + 1 です。自然数・加法・等式も同じ固定版の Lean 同梱定義を参照するため、これらの参照先を含めて一致します。出題側の `sorry` と解答側の証明項は異なりますが、型と参照定義を比較する条件には反しません。Lean の `theorem addZeroLeft (n : Nat) : 0 + n = n` は `∀ n : Nat, 0 + n = n` という型を持ちます。`stepRefl` も同じ全称量化で、型から `step` の名前をたどって宣言本体 `fun n : Nat => n + 1` を比較します。実装は [Compare.lean](https://github.com/leanprover/lean4/blob/v4.35.0/src/lake/Lake/Check/Compare.lean) の `compareAt` と `Compare.loop` で、対象定理の型から参照先をたどります。

一方、解答側の step の定義を n ↦ n + 2 に変更すると、0での値は1から2へ変わります。参照する定義が異なるので、後者の定理の文字列が同じでも照合は不合格です。
<!-- definition-example-end -->

この照合は任意の二つの数学的命題の論理的同値性を決定する手続きではありません。同値だと思う別の定式化を利用したい場合は、出題側の型へ戻す橋渡しの証明を解答側に作ります。また照合に成功しても、出題側の型と自然言語の数学的主張が一致するかは別に確認します。[数学的主張の条件と適用範囲](../FML5/index.md#def-fml5-claim) に従い、量化される対象と追加仮定を一つずつ読みます。

## 2. 証明の再検査をどこまで信頼するか

カーネルは型理論の規則に従い、定義や証明項を検査する部分です。タクティクが作った証明項を別に検査できるため、タクティクの計算方法が違っても同じ型の証明であればよいのです。証明を別のカーネルに渡すためには、宣言や式を読み直せる形式へ書き出します。この書き出されたデータをエクスポートと呼びます。Lean 4.35.0 の Comparator は同梱の leanexport によって書き出し、型および参照宣言の照合と解答側の公理検査を行い、解答のエクスポートをカーネルで検査します。

nanoda は Lean のカーネルを Rust で独立に実装した検査器です。同じ Lean カーネルを別のPCで二回動かすことと、異なる実装で同じエクスポートを検査することを区別します。前者は環境の再現性の検査に役立ち、後者は実装固有の誤りに対する検査を増やします。

判定の組み立てを明示しましょう。対象定理を $T$、出題者が許容する公理名の集合を $S$ とします。[数学的証明の許容公理集合](../FML5/index.md#def-fml5-policy) に従い、解答の型と証明値からたどる公理依存集合 $\operatorname{Ax}(T)$ が $S$ に含まれるかを調べます。$M$ は [定理ステートメント照合](#def-fml6-statement-matching) の成否、$A$ はこの公理条件の成否とし、成功なら1、失敗なら0とします。

検査器の数を正の整数 $m$ とし、$i=1,\ldots,m$ は検査器の番号です。$K_i$ は $i$ 番目の検査器が、照合・公理検査で調べた解答エクスポートを受理したとき1、それ以外は0とします。$\prod_{i=1}^{m}K_i$ はこれら $m$ 個の判定値の積です。

<a id="def-fml6-multikernel"></a>

<!-- formal-statement-start -->
### 定義（複数カーネルによる受入条件）

固定された出題環境、解答環境、対象定理 $T$、許容公理集合 $S$、および $m\geq 1$ 個の検査器を指定する。出題データおよび解答データを固定し、同じ解答エクスポートに対してステートメント照合 $M$ と公理条件 $A$ が成功し、さらにすべての指定検査器が受理したとき、その解答を受け入れる。すなわち、

$$
M A\prod_{i=1}^{m}K_i=1
$$

が受入条件である。ただし各判定値は0または1とする。
<!-- formal-statement-end -->

<!-- definition-example-start: def-fml6-multikernel -->
**定義の確認**　$S$ を propext、Quot.sound、Classical.choice の集合とします。第1節の二環境の `stepRefl` を対象にすれば、型と参照定義が一致するので $M=1$ です。反射律だけを用いる解答では追加公理に依存せず、$\operatorname{Ax}(T)=\varnothing\subseteq S$ なので $A=1$ です。同じ解答エクスポートを二つの検査器が受理した場合を考えます。$m=2$、$K_1=K_2=1$ なので、

$$
MAK_1K_2=1\times1\times1\times1=1
$$

となり受け入れます。一方、$K_2=0$ なら積は0です。照合で $M=0$ となる場合や公理検査で $A=0$ となる場合も、両検査器の受理とは無関係に積は0です。
<!-- definition-example-end -->

ある検査器が健全であるとは、ここでは受理した証明データが所定の型理論と指定公理の下で実際に妥当であることを意味します。これは検査器の正しさについての仮定です。検査器の数を増やしても、健全性を自動的に証明したことにはなりません。

<a id="prop-fml6-sound"></a>

<!-- formal-statement-start -->
### 命題（全検査の受入と健全な検査器）

固定された出題・解答環境と対象定理について、出題データと解答エクスポートがそれぞれの環境を正しく表し、正しいステートメント照合と公理検査が行われるとする。照合・公理検査と同じ解答エクスポートを検査する $m$ 個（$m\geq 1$）の検査器のうち少なくとも一つが指定公理の下で健全だと仮定する。すべての検査器が受理し、ステートメント照合と公理検査も成功したなら、出題された形式的主張は指定公理の下で妥当な証明を持つ。
<!-- formal-statement-end -->

見取り図：全員が受理したなら、どの検査器が健全かを知らなくても、その検査器の受理を利用できます。さらに型の照合によって解答側の結果を出題側の主張に戻します。

<!-- proof-start -->
### 証明

[複数カーネルによる受入条件](#def-fml6-multikernel) により各判定値が1である。健全な検査器の番号を $j$（$1\leq j\leq m$）とすると、全検査器が受理しているため $K_j=1$ である。健全性をその検査器に渡した解答エクスポートに適用すると、そこに記録された解答側の型の妥当な証明が得られる。エクスポートの正しさと同一性の仮定により、これは照合・公理検査の対象にした解答の証明である。

[数学的証明の許容公理集合](../FML5/index.md#def-fml5-policy) の条件より、$A=1$ から $\operatorname{Ax}(T)\subseteq S$ が従う。[定理ステートメント照合](#def-fml6-statement-matching) の成功により、その型と解釈に必要な宣言は出題側のものと一致する。従ってこの証明は出題側の形式的主張の証明として成立する。
<!-- proof-end -->

例えば二検査器のうち一つが誤って任意のデータを受理しても、他方が健全であれば、誤った証明は他方で拒否されます。一方、両検査器が同じ誤りを持つ場合や、書き出しの段階で別の証明データへすり替わった場合には、上の仮定が破れます。カーネルの独立性は同一の出題定義・エクスポート・公理方針を検証する必要をなくしません。

## 3. 小さな証明を実際に照合する

[LVTの固定されたLeanプロジェクト](../../LVT/LVT1-02/index.md#def-lvt1-02-fixed-environment) を再利用します。本講の lab は Lean 4.35.0 固定で、外部パッケージはありません。Comparator は4.35.0で Lake へ統合されたため、旧 comparator リポジトリを別途ビルドする必要はありません。

出題側 [Challenge.lean](lab/Challenge.lean) と解答側 [Solution.lean](lab/Solution.lean) は同じ定義と型を持ちます。以下は解答側の中心部分です。

```lean
namespace FML6

def step (n : Nat) : Nat := n + 1

theorem addZeroLeft (n : Nat) : 0 + n = n := Nat.zero_add n
theorem stepRefl (n : Nat) : step n = step n := rfl

end FML6
```

addZeroLeft では自然数の加法の左零元の既存 Lean 補題 `Nat.zero_add` を $n$ に適用します。加法の再帰規則 $a+0=a$、$a+(k+1)=(a+k)+1$ で確かめましょう。$n=0$ では $0+0=0$ です。$n=k$ で $0+k=k$ と仮定すると、$n=k+1$ では

$$
0+(k+1)=(0+k)+1=k+1
$$

となります。最初の等号は加法の再帰規則、次の等号は帰納法の仮定によります。帰納法で全自然数について成立します。stepRefl では両辺の step n が同一の式なので反射律で閉じます。出題側では二定理の型をそのまま保存し、証明項だけを sorry にしています。

[comparator.json](lab/comparator.json) は出題・解答のモジュール名、検査対象の二定理、許容公理名を指定します。theorem_names は完全修飾名（名前空間を含む名前）の配列です。

```json
{
  "challenge_module": "Challenge",
  "solution_module": "Solution",
  "theorem_names": ["FML6.addZeroLeft", "FML6.stepRefl"],
  "permitted_axioms": ["propext", "Quot.sound", "Classical.choice"]
}
```

Linux の非特権ユーザー環境で bubblewrap（bwrap）を利用できるようにし、固定版の Lean を用意します。未信頼ソースを扱うときには、出題者側の設定と依存を自分で確保し、機密情報のない隔離環境で検証します。出題側を信頼できないソースによって上書きさせないことも大切です。

リポジトリのルートから以下を実行します。

```bash
cd "textbook/volumes/dream_thater/計算系/FML/FML6/lab"
lean --version
lake --version
bash verify.sh
```

[verify.sh](lab/verify.sh) は検査ごとに一時ディレクトリへソースと設定を複製し、生成物 .lake がない状態から開始します。正例では lake comparator --paranoid を実行し、Lean 本体に加えて同梱の外部検査器（nanoda など）を実行します。Lean 4.35.0 の [CLI実装](https://github.com/leanprover/lean4/blob/v4.35.0/src/lake/Lake/CLI/Check.lean) と [ヘルプ](https://github.com/leanprover/lean4/blob/v4.35.0/src/lake/Lake/CLI/Help.lean) で対象版の動作を確認できます。旧 comparator の導入手順とは異なります。

終了コード0と nanoda の受理、最終の成功メッセージを確認します。ログの保存先はスクリプトの冒頭に表示されます。実行時にエラーが生じたら、終了コード2（設定や必要ツール等の開始前の問題）と、終了コード1（拒否またはビルド失敗）を区別します。終了コード1だけで型不一致と判断してはいけません。

## 4. 負のテストで検査対象を確かめる

解答側を次のように変え、出題側を固定します。それぞれのファイルは単独なら型検査に成功するように設計しています。

| 解答側 | 変更 | 期待される比較結果 |
| --- | --- | --- |
| [Solution.lean](lab/Solution.lean) | 証明のみ完成 | 受理 |
| [Mismatch.lean](lab/Mismatch.lean) | addZeroLeft に h : n = 0 を追加 | 型の照合で拒否 |
| [ChangedDefinition.lean](lab/ChangedDefinition.lean) | step の定義を n + 2 に変更 | 参照定義の照合で拒否 |
| [ForbiddenAxiom.lean](lab/ForbiddenAxiom.lean) | 独自公理 externalProof で左零元を証明 | 公理検査で拒否 |

Mismatch では出題型が `∀ n : Nat, 0 + n = n` なのに対し、解答型は `∀ n : Nat, n = 0 → 0 + n = n` です。[数学的主張の条件と適用範囲](../FML5/index.md#def-fml5-claim) の区別を $n=1$ に適用すると、前者から $0+1=1$ の証明を得る一方、後者から得るのは

$$
1=0\ \Longrightarrow\ 0+1=1
$$

という条件付き主張です。追加の引数 $h$ に $1=0$ の証明を渡せないので、そのまま同じ方法では利用できません。型の構造が異なることが拒否理由です。

ChangedDefinition では stepRefl の証明自体は反射律で通ります。しかし出題側の step 0=1 に対して解答側の step 0=2 です。比較の目的は反射律の証明が可能かだけでなく、出題された定義の下でその型が証明されたかを確認することです。

ForbiddenAxiom では addZeroLeft の型を維持しますが、証明値は externalProof n です。[数学的証明の許容公理集合](../FML5/index.md#def-fml5-policy) で許した三公理に externalProof は含まれないので拒否します。これは左零元の等式が偽という意味ではありません。許された証明経路が提示されなかったという判定です。

エクスポートを直接受け取って比較する方法もあります。その場合は --challenge-from-export と --solution-from-export が使えますが、そのデータがどのソースから作られたかまでは比較コマンドが証明しません。ソースのコミット、依存の固定情報、生成コマンド、検証ログ、データのハッシュ（内容を識別するための値）を照合します。データのハッシュが一致しても数学的な主張と出題の意図との一致は別の問題です。

### FML6-A02 型と証明値

addZeroLeft の証明を出題側の sorry から解答側の Nat.zero_add n へ変更した。何が変わり、何が変わらないか。

- Level: A

<!-- solution-start -->
#### 詳細解答

型は任意の自然数 $n$ に対する $0+n=n$ のままである。値は未完成証明から自然数の左零元の補題を $n$ に適用した証明へ変わる。第3節の加法の再帰規則で基底 $0+0=0$ を得る。$0+k=k$ を仮定した帰納段階では、

$$
0+(k+1)=(0+k)+1=k+1
$$

である。[定理ステートメント照合](#def-fml6-statement-matching) は型と必要な参照定義が一致することを調べるため、証明値が異なること自体は拒否理由にならない。解答の公理依存とカーネル受理は別途調べる。
<!-- solution-end -->

### FML6-A03 追加仮定

全自然数 n に対する 0+n=n と、n=0 を仮定した 0+n=n の型の違いを n=2 で説明せよ。

- Level: A

<!-- solution-start -->
#### 詳細解答

前者に2を渡せば 0+2=2 の証明を直接得る。後者には2を渡した後、2=0 の証明をさらに渡す必要がある。2は0と異なるのでその引数を提供できない。[数学的主張の条件と適用範囲](../FML5/index.md#def-fml5-claim) に従えば後者の適用範囲は n=0 に限定される。従って二つの型は同一のステートメントではない。
<!-- solution-end -->

### FML6-A04 受入判定

M=1、A=1、三つのカーネルの判定値が順に1、0、1の場合と、すべて1の場合の判定を計算せよ。

- Level: A

<!-- solution-start -->
#### 詳細解答

[複数カーネルによる受入条件](#def-fml6-multikernel) の積を計算すると、前者は 1×1×1×0×1=0 なので拒否する。後者は 1×1×1×1×1=1 なので受入条件を満たす。検査器の多数決ではなく全員の受理を要求する。
<!-- solution-end -->

### Level B

### FML6-B01 参照定義の変更

出題側の step n=n+1 と解答側の step n=n+2 の下で step n=step n の証明がともに存在することを示し、照合が拒否する理由を述べよ。

- Level: B

<!-- solution-start -->
#### 詳細解答

出題側で展開すると両辺は n+1、解答側で展開すると両辺は n+2 なので、いずれも反射律 rfl が利用できる。しかし [定理ステートメント照合](#def-fml6-statement-matching) では型中の step の定義も比較する。n=0 を代入すると出題側は0+1=1、解答側は0+2=2で値が異なるため、同じ定義とはいえない。反射律の妥当性ではなく参照対象が不一致であることが拒否理由となる。
<!-- solution-end -->

### FML6-B02 二つの検査器の健全性

検査器 K_1 が常に受理し、K_2 は健全であるとする。M と A が成功したとき、両方の受理から何を結論できるか。逆に両方が常に受理する場合も考えよ。

- Level: B

<!-- solution-start -->
#### 詳細解答

出題・解答のエクスポートが正しく、照合・公理検査と両検査器が同じ解答データを調べるという前提で考える。両方の受理から $K_2=1$ が得られる。第2検査器の健全性をそのデータに適用すると指定公理の下で証明が妥当であり、$M=1$ により出題側の型に対応する。[全検査の受入と健全な検査器](#prop-fml6-sound) の仮定を満たす。両方が常に受理するなら、誤ったデータも K_1=K_2=1 となる。例えば自然数1と2の等式を証明したと称する無効な項も受け入れてしまう。少なくとも一つの健全な検査器という仮定が欠けているため、命題を適用できない。
<!-- solution-end -->

### FML6-B03 負のテストの診断

Mismatch の検証が終了コード1を返した。ログにはファイルの import に失敗したとだけ書かれていた。この観測から型の照合機構が正しく機能したと結論できるか。検査を設計し直せ。

- Level: B

<!-- solution-start -->
#### 詳細解答

終了コード1にはビルド失敗も含まれるので、import の失敗は型比較に到達した証拠ではない。まず固定環境で Solution の比較を実行し成功を確かめる。次に Mismatch 単独のビルドを確認する。その生成物を削除した上で独立した出題側と比較し、addZeroLeft の型の不一致を示す診断を確認する。失敗ログが依存取得や別のエラーなら型の比較を検証したことにはならない。正例と負例の実行結果を対にして保存する。
<!-- solution-end -->

### Level C

### FML6-C01 証明受領から受入までの設計

研究者が全自然数 n で 0+n=n と述べ、さらに step n=n+1 と定めた上で step n=step n を主張し、エクスポートと「二カーネル成功」の報告を渡した。別の出題者として再検証手順を設計せよ。型の変更、定義の変更、追加公理の三つをそれぞれどこで検出するか、また自然言語とエクスポートの由来について残る確認を説明せよ。

- Level: C

<!-- solution-start -->
#### 詳細解答

最初に自然言語の全自然数を Lean の Nat の全称量化、左の加法を標準の自然数加法、等号を Nat の等式に対応させ、出題環境に addZeroLeft の型を固定する。余分な条件は付けない。さらに step の定義を n+1 と固定し、stepRefl の型を step n=step n として比較対象に含める。ソース、コミット、固定版、設定と manifest を独立に保存する。

次に解答側を別環境で構築し、[定理ステートメント照合](#def-fml6-statement-matching) を行う。仮定 n=0 が追加されると n=1 の場合に 1=0 を要求する関数型に変わり、型の照合で拒否される。step が変更された場合には n=0 で値1と2の差が出るため、参照宣言の照合で拒否される。続いて [許容公理集合](../FML5/index.md#def-fml5-policy) により externalProof のような許容外の依存を拒否する。

正例について照合・公理検査で用いた解答エクスポートと同じデータを各カーネルへ渡し、個別の終了状態とログを保存する。M=A=1、すべての K_i=1 なら [全検査の受入と健全な検査器](#prop-fml6-sound) の仮定の下で受入可能となる。三つの負例はそれぞれ単独のビルドを確認し、対応する拒否理由を記録する。

最後に受け取ったエクスポートが報告されたソースの固定コミットから生成されたか、生成コマンド、ハッシュ、独立した再構築結果を照合する。自然言語の主張と出題型の対応は型理論の検査器が決めるものではないので、人が量化、定義、仮定を確認する。こうして形式的証明の妥当性と研究上の主張の妥当性を分けて扱える。
<!-- solution-end -->
