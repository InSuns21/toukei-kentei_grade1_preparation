# LVT5-02 Lean実行可能仕様のJSON Linesオラクル化

前提講座：[LVT5-01 Differential Testing・オラクルの設計](../LVT5-01/index.md)、[LVT1-06 純粋な参照モデルと入出力境界](../LVT1-06/index.md)、[LVT3-01 要求を事前条件・事後条件へ](../LVT3-01/index.md)。

前講の [観測付き差分検査](../LVT5-01/index.md#def-lvt5-01-observed) では、Leanと別実装の同じ入力に対する出力を比較しました。しかし外部のプログラムはLeanの関数を直接呼べません。そこで文字列として入力を受け取り、文字列として応答する窓口を作ります。正しい関数であっても、窓口で入力を取り違えたり、応答を落としたりすると検査は壊れます。

**ブラウザで実行：** [本講の実行ラボ](../browser-lab.html?chapter=LVT5-02)。純粋な応答生成と証明はLean Web、実際の入出力は同じラボからCodespacesで試します。

## 1. 在庫引当を文字列で呼ぶ

JSONはオブジェクト、配列、文字列、数値、真偽値、nullなどの値を文字で表す形式です。JSON Linesでは一行に一つのJSON値を書き、改行で区切ります。改行を含む文字列はJSON中でエスケープ（例えば \n）し、実際の改行と区別します。

今回の要求には文字列の識別子 id、非負整数（Lean の `Nat` は0を含む）の在庫 stock と数量 qty を入れます。識別子は入力と応答の照合に使います。同じ接続中で正常な要求のidを区別できるようクライアントが異なる文字列を選びます。識別子が同じでもサーバーは重複排除しません。キーの重複しないオブジェクトをクライアントの送信形式とし、未知の追加フィールドは本実装では無視します。自然数として読めるかどうかはLeanのJSONデコーダーが判定します。

~~~json
{"id":"a","stock":5,"qty":2}
{"id":"b","stock":2,"qty":2}
{"id":"c","stock":1,"qty":2}
{"id":"d","stock":4,"qty":0}
~~~

[在庫引当関数の契約充足](../LVT3-01/index.md#prop-lvt3-01-correct) と [在庫引当仕様の結果一意性](../LVT3-01/index.md#prop-lvt3-01-unique) によって、正の数量の要求に対する takeStock の結果を比較基準とできます。数量0は関数が別途拒否します。成功時の応答には残数 rest、拒否時には status=rejected を入れます。数量0もここでは正常に解析された業務上の拒否です。構文不正、必須フィールド不足、型不一致は業務上の拒否と区別し、status=error と code=invalid_request、id=null を返します。エラー行の識別子は信用せず、行位置で対応させます。

| 入力 | 結果 | 理由 |
|---|---|---|
| a | {"id":"a","status":"ok","rest":3} | 2≤5、3+2=5 |
| b | {"id":"b","status":"ok","rest":0} | 2≤2、0+2=2 |
| c | {"id":"c","status":"rejected"} | 1<2 |
| d | {"id":"d","status":"rejected"} | 数量0 |
| { | {"id":null,"status":"error","code":"invalid_request"} | 閉じ括弧がなく構文不正 |

JSONオブジェクトのキー順は比較対象にしません。応答の意味を比較するために、外部側でもJSONを解析してオブジェクトを照合します。

## 2. 一行から一応答へ

一行を解析し、成功なら業務関数を適用して応答を組み立て、失敗ならエラーを組み立てます。行の集合を X（改行を区切りとして除いた文字列の集合）、応答JSON値の集合を Y とします。空行も入力として扱い、EOF（入力の終了）とは区別します。各行について必ず計算が終わり、同じ行には常に同じ応答を返す（決定的である）関数を考えます。[純粋な関数](../LVT1-06/index.md#def-lvt1-06-pure-function) として、今回の応答関数を $a:X\to Y$ と書きます。$a(x)$ は入力行 $x$ に対する応答値であり、要求の識別子 `"a"` とは別の記号です。有限列 $(x_1,\ldots,x_n)$ の $n$ は行数（0以上）、$x_i$ は第 $i$ 行です。

<a id="def-lvt5-02-line-oracle"></a>

<!-- formal-statement-start -->
### 定義（行単位オラクル契約）

X を入力行の集合、Y を応答値の集合とし、a:X→Y を終了する決定的な関数とする。有限な入力列 (x₁,…,xₙ) に対し、応答列は (a(x₁),…,a(xₙ)) であり、各入力に一つだけ同じ位置の応答が対応する。解析できない入力も X に属する場合は a の定義域に含める。
<!-- formal-statement-end -->

<!-- definition-example-start: def-lvt5-02-line-oracle -->
**定義の確認**　X は入力文字列、Y はJSON値とする。第1節の処理では有限の文字列を解析し、失敗なら固定のエラー値、成功なら [在庫引当関数の契約充足](../LVT3-01/index.md#prop-lvt3-01-correct) に従う比較・減算の結果から一つの応答値を組み立てる。外部状態を参照しないので、各行で終了し決定的である。入力列を、識別子 `"a"` の要求、文字列 `{`、識別子 `"b"` の要求の順に取る。第1行は数量2が正で $2\le5$、残数 $5-2=3$。第2行はJSON構文不正なので固定のエラー値。第3行は数量2が正で $2\le2$、残数 $2-2=0$。各行の応答値を順に並べると [成功（残数3）, エラー, 成功（残数0）] になる。入力3行すべてに応答が1件ずつあり順番も保つ。解析エラーを捨てて2行にするとこの契約を満たさない。
<!-- definition-example-end -->

## 3. バッチと逐次処理

バッチとは全入力を受け取った後でまとめて結果を返す方法です。持続プロセスとは、起動後に一行を受け取るたびに応答して、次の行を待つプロセスです。終了したプロセスを毎回作り直す必要がありません。両者の純粋な応答列を比較しましょう。空列を `[]`、先頭要素 `x` を残りの列 `xs` の前に付ける操作を `x::xs` と書きます。これは入力行の文字列連結ではなく、リストに要素を一つ追加する操作です。$X^*$ は $X$ の要素からなる全有限列の集合、$Y^*$ は応答値の全有限列の集合、$\operatorname{length}(xs)$ は列の要素数です。バッチモデル $B:X^*\to Y^*$ は各要素への $a$ の適用（Lean の `List.map`）、逐次モデル $S:X^*\to Y^*$ は空列なら `[]`、先頭が `x` なら $a(x)$ を先に置いて残りへ $S$ を適用する関数です。Lean の `batchModel`、`streamModel`、`answer` がそれぞれ $B,S,a$ に対応します。

<a id="prop-lvt5-02-batch-stream"></a>

<!-- formal-statement-start -->
### 命題（バッチと逐次応答列の一致）

[行単位オラクル契約](#def-lvt5-02-line-oracle) の応答関数 a を固定する。任意の有限列 xs∈X* に対し、B(xs) を a の要素ごとの適用、S([])=[]、S(x::xs)=a(x)::S(xs) とする。このとき S(xs)=B(xs) かつ両応答列の長さは入力列の長さに等しい。従って応答の順序も一致する。
<!-- formal-statement-end -->

**証明の見取り図**　先頭の応答は両者とも a(x) です。残りの列で一致すると仮定して先頭を付ければ、全体でも一致します。

<!-- proof-start -->
### 証明

[リストの帰納法](../LVT2-05/index.md#principle-lvt2-05-list) を使う。空列では S([])=[]、B([])=[] だから一致し、長さはいずれも0である。

帰納段階では x∈X と有限列 xs を取り、S(xs)=B(xs) および length(B(xs))=length(xs) を仮定する。先頭 x へ a を適用し、残りの列へ List.map を適用するので B(x::xs)=a(x)::B(xs)。従って

$$
S(x::xs)=a(x)::S(xs)
$$

$$
=a(x)::B(xs)=B(x::xs).
$$

最初の等号は S の再帰式、次の等号は帰納仮定 S(xs)=B(xs) を先頭に a(x) を付ける関数へ適用したもの、最後は上の B(x::xs) の展開である。また先頭を一つ加えた列の長さは残りの長さに1を加えたものなので

$$
\operatorname{length}(B(x::xs))=1+\operatorname{length}(B(xs))
$$

$$
=1+\operatorname{length}(xs)=\operatorname{length}(x::xs).
$$

一致する列 S も同じ長さを持つ。有限列は空列または先頭と有限な残りから構成されるため、帰納法で全有限列について成立する。列の等しさは各位置の値の等しさを含むので、順序も一致する。
<!-- proof-end -->

[入出力境界](../LVT1-06/index.md#def-lvt1-06-io-boundary) の外側では、入力バイトの読み込み、JSONの解析と出力、バッファリング、OSによるプロセス終了などが加わります。この命題は純粋な列モデルの定理です。例えば逐次モードで応答をメモリに貯めてEOFまで送信しなければ、数学的には同じ応答列でも、次の入力を送る前に応答を待つクライアントは停止してしまいます。

## 4. 実際の入出力の設計

標準入力 stdin から要求を受け取り、標準出力 stdout には応答だけを書きます。人間向けの診断は標準エラー出力 stderr に分離します。stdout に「起動しました」のような文字列を出すと、それを1件目の応答として読もうとするプログラムはJSON解析に失敗します。

バッチではクライアントが全行を送信し、stdinを閉じてEOFを伝えた後、応答列と終了コードを読みます。持続モードでは一行を送ったら書き込みをフラッシュ（バッファに留めたデータを送り出す操作）し、相手も一行応答してフラッシュします。次の要求の前に応答を待つ方式なので、相手がEOFまで待っていないことを確かめられます。エラー行も応答して次へ進みます。空行は改行文字（LF）があるためEOFと異なり、エラー応答になります。本実装では非空の末尾行にLFがなくても処理します。Lean の `getLine` が返す文字列に末尾のLFが残っていても、JSON解析では末尾の空白として扱われるため、区切りを除いた行を解析するモデルと結果は同じです。

| 状況 | クライアントの確認 |
|---|---|
| 正常要求 | status、id、残数の全値 |
| 解析不能 | その位置でエラー1件、後続行も処理 |
| 空入力でEOF | 応答0件、正常終了 |
| 応答待ち | 時間上限を超えれば検査失敗 |
| 終了 | 余分なstdoutがなく終了コード0 |
| 不正な起動引数 | stdoutなし、stderrに診断、終了コード2 |

実行環境の異常終了や資源枯渇を業務上の拒否として扱ってはいけません。時間上限、終了コード、欠落応答も検査の失敗にします。今回の実験は有限の小さな入力を対象にし、文字列のバイト数に上限を設けない場合、バッチのメモリ使用量、同時要求の相関、重複キーの扱いなどは別途契約が必要です。

## 5. LeanとPythonで実験する

[応答生成と証明](lab/LvtOracle.lean) は decode でJSONを解析し、answer で takeStock の結果をJSONに戻します。batchModel は List.map、streamModel は構造再帰です。streamEq と responseCount が [バッチと逐次応答列の一致](#prop-lvt5-02-batch-stream) を表します。[CLI](lab/Main.lean) の collect は読み取った行を逆順に蓄え、EOFで反転して入力順に戻します。serve は一行ごとに answer を出力し、フラッシュしてから次へ進みます。ここでは入出力ループそのものをLeanで全称証明しているわけではありません。

~~~bash
cd "textbook/volumes/dream_thater/計算系/LVT/LVT5-02/lab"
lean --version
lake build
lake test
lake env lean LvtOracle.lean
printf '%s\n' '{"id":"a","stock":5,"qty":2}' '{' | .lake/build/bin/lvtOracle --batch
python3 compare.py
# 意図的に誤った証明
lake env lean Failure.lean
~~~

Leanの固定版は4.35.0です。テストドライバは LVT5-02 OK を出力します。CLIの2行は成功（残数3）と解析エラーです。Lean Webでの計算は固定版と異なる場合があります。Codespacesの利用にはログインと利用枠が必要です。

[Pythonの外部検査](lab/compare.py) では、残数を0から在庫まで探索し、rest+qty=stock かつ qty>0 を満たすか調べて期待値を作ります。25件について、バッチと持続の両モードで同じ期待値を全項目照合します。残数は整数表現を要求します。Pythonでは `True == 1` が成立するため、単なる辞書の等値比較では残数の型違いを見逃します。そこで解析済みの値をキー順をそろえてJSON文字列に戻し、`true`、`1`、`1.0` の違いを保って比較します。これは本講の応答形式に合わせた判定であり、任意のJSON数値の同値性や重複キーの検査は別の問題です。識別子には引用符と改行を含む例も入れます。持続モードは一行ずつ送信してEOF前の応答を期限付きで読み、最後にEOF、余分な応答、終了コードを検査します。空入力と不正な起動引数も試します。正常時の最後の表示は LVT5-02: 25 ordered responses in each mode; EOF and CLI checks OK です。

Failure.lean では在庫と数量が等しいときに拒否するという誤った等式が型不一致になります。これは業務仕様の境界値であり、解析エラーとは別です。stdoutの純度・応答順・プロセス寿命を確認する外部検査と、モデルの定理を確認する証明は互いに補い合います。

## 6. 演習と詳細解答

### Level A

### LVT5-02-A01 正常応答の構成

{"id":"z","stock":7,"qty":3} に対する応答を求めよ。

- Level: A

<!-- solution-start -->
#### 詳細解答

文字列idと自然数7,3が解析できる。数量3>0かつ3≤7なので成功し、残数7−3=4（4+3=7）。従って {"id":"z","status":"ok","rest":4}。識別子も要求のまま返す。
<!-- solution-end -->

### LVT5-02-A02 拒否と解析エラー

{"id":"b","stock":1,"qty":2} と {"id":"b","stock":1} の応答を区別せよ。

- Level: A

<!-- solution-start -->
#### 詳細解答

前者は三フィールドがそろい、数量2>1なので {"id":"b","status":"rejected"}。後者は qty が欠けているので takeStock に渡せず、{"id":null,"status":"error","code":"invalid_request"}。在庫不足と入力形式不正は別の状態である。
<!-- solution-end -->

### LVT5-02-A03 空行とEOF

空行1件を送ってからEOFを送る場合と、何も送らずEOFを送る場合の応答数を求めよ。

- Level: A

<!-- solution-start -->
#### 詳細解答

前者はLFだけの一行が読み取られ、JSON値がないためエラー応答1件。その後EOFで終了する。後者は最初の読み取りがEOFで、処理対象の行は0件。従って応答0件となる。
<!-- solution-end -->

### LVT5-02-A04 stdoutの混入

CLIが応答前に ready と改行をstdoutに出した場合、正常な要求1件に対する検査はどうなるか。

- Level: A

<!-- solution-start -->
#### 詳細解答

受信行は ready と本来のJSON応答の2行になる。ready はJSON値ではないので最初の行の解析が失敗し、仮に読み飛ばしても応答は1件という契約を破る。診断はstderrへ移す。
<!-- solution-end -->

### Level B

### LVT5-02-B01 列モデルの展開

入力列 [x,y,z] で a(x)=成功、a(y)=エラー、a(z)=拒否とする。BとSを空列まで展開し、長さと順序を確認せよ。

- Level: B

<!-- solution-start -->
#### 詳細解答

B([x,y,z])=[a(x),a(y),a(z)]。S([x,y,z])=a(x)::S([y,z])=a(x)::a(y)::S([z])=a(x)::a(y)::a(z)::S([])。S([])=[] を代入すると [成功,エラー,拒否] となりBと一致する。空列の長さ0に先頭を3回追加するので長さ3。エラーを捨てると長さ2で第3入力の応答位置がずれる。[バッチと逐次応答列の一致](#prop-lvt5-02-batch-stream) の3要素の場合である。
<!-- solution-end -->

### LVT5-02-B02 持続プロセスの停止

クライアントは要求を1行送って応答を受け取ってから次を送る。サーバーがEOFまで全入力を待って応答する場合、何が起こるか。相互待ちを解消する方法と検査方法を述べよ。

- Level: B

<!-- solution-start -->
#### 詳細解答

クライアントは応答待ちで、次の行もEOFも送らない。サーバーはEOF待ちで応答を出さないため双方が進めない。逐次モードでは一行受け取ったら解析・応答生成・出力・フラッシュを終えてから次の読み取りに移る。検査側はstdinを閉じずに1件目の応答を期限付きで受信し、同じプロセスへ2件目を送る。応答が来なければ時間超過を失敗としてプロセスを回収する。
<!-- solution-end -->

### LVT5-02-B03 識別子と順序

同じ在庫5、数量2の要求をid=a, id=bの順で送る。二つの応答のidが逆順だった場合、残数だけの比較で何が失われるか。

- Level: B

<!-- solution-start -->
#### 詳細解答

両要求で残数5−2=3。残数列は [3,3] で逆順でも区別できない。しかし期待するid列は `["a","b"]`、実際は `["b","a"]` で、第1位置で `"a" ≠ "b"`、第2位置で `"b" ≠ "a"`。行単位の対応を保つには各位置のidを含む全応答を比較する。[正しい基準との一致による適合性](../LVT5-01/index.md#prop-lvt5-01-agreement) の観測を残数だけに狭めると、識別子の正しさまでは従わない。
<!-- solution-end -->

### Level C

### LVT5-02-C01 二つの起動方式の検査

次の4行を使い、バッチと持続モードの期待応答を求めよ。Pythonスクリプトで実行し、正常・エラー・終了の検査を説明せよ。さらにモデルの証明と外部検査で何が保証されるか区別せよ。

~~~json
{"id":"p","stock":3,"qty":1}
{
{"id":"q","stock":3,"qty":3}
{"id":"r","stock":0,"qty":1}
~~~

- Level: C

<!-- solution-start -->
#### 詳細解答

p は1≤3、2+1=3なので残数2の成功。2行目は構文不正のためid=nullのエラー。q は3≤3、0+3=3なので残数0の成功。r は0<1のため拒否。期待列は次の4件である。

~~~json
{"id":"p","status":"ok","rest":2}
{"id":null,"status":"error","code":"invalid_request"}
{"id":"q","status":"ok","rest":0}
{"id":"r","status":"rejected"}
~~~

ラボのディレクトリで次を実行する。期待値は上で手計算した4件をそのまま設定する。

~~~python
from compare import run_batch, run_stream, request, ERROR
rows = [
    (request("p", 3, 1), {"id":"p", "status":"ok", "rest":2}),
    ("{", ERROR),
    (request("q", 3, 3), {"id":"q", "status":"ok", "rest":0}),
    (request("r", 0, 1), {"id":"r", "status":"rejected"}),
]
want = [v for _, v in rows]
assert run_batch(rows) == want
assert run_stream(rows) == want
~~~

バッチでは全4行送信後にEOFを送り、4件のJSON応答と正常終了を確認する。持続では1行ごとに送信・フラッシュ・期限付き受信を4回繰り返す。2行目のエラーの後でqが成功するので、エラーでプロセスを終わらせていないことも分かる。EOF後は余分な行がなく終了コード0であることを確認する。[バッチと逐次応答列の一致](#prop-lvt5-02-batch-stream) は任意の有限入力列に対する純粋なモデルの等しさを保証する。実際のCLIがそれを実現することはここでの4行および通常の25件について実行検査するものであり、全バイト列や全OS動作の証明ではない。
<!-- solution-end -->

## 7. 次の講義へ

次講では直列化・正規化・一致判定を掘り下げ、異なる言語の数値や構造をどのように同じ意味として比較するかを検討します。
