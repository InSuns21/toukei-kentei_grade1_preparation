# 通常教材の執筆スタイルガイド（差分）

通常教材は次の共通正本を継承する。

- 全教材共通規約：[`../CONTENT_GUIDELINES.md`](../CONTENT_GUIDELINES.md)
- 演習・詳細解答・本番答案・採点基準：[`../EXERCISE_GUIDELINES.md`](../EXERCISE_GUIDELINES.md)
- 一般記号：[`../references/notation-guide.md`](../references/notation-guide.md)
- 分布規約：[`../references/distribution-notation-guide.md`](../references/distribution-notation-guide.md)
- 用語・略語：[`../references/terminology-guide.md`](../references/terminology-guide.md)

このファイルには**通常教材だけに必要な表示・説明粒度・運用上の差分**だけを書く。数式記法、用語、分布表記、詳細解答の行間、定理適用、電卓利用などの共通規則はここで再定義しない。

章の具体的な見出し構成・配置順・solution markerの置き方は [`templates/chapter/index.md`](templates/chapter/index.md) を唯一の正本とする。新規章は `npm run new:chapter -- <章ID>` でこのテンプレートから作成する。`textbook/templates` は執筆用の内部資産であり、GitHub Pagesの読者向け公開対象には含めない。

## 1. 読者と到達点

読者は大学初年度の微積分・線形代数を履修済みで、統計検定1級を独習する受験者とする。通常教材は、概念の導入から演習へ段階的につなぎ、最終的に本番で採点可能な答案を書ける状態へ導く。

### 1.1 通常教材本文の説明粒度

通常教材の本文は、統計数理100や理工80の詳細解答とは役割が異なる。数学的に正確であることは必要だが、**厳密性のための専門語を先に置いて読者へ定義を解読させない**。

本文では原則として次の順序を使う。

1. 何を表す量・分布なのかを日本語で説明する。
2. まず2変量・1母数・具体的な数値例など最小の例を置く。
3. その例を一般式へ広げる。
4. 必要なら導出を示す。
5. 公式出題範囲を超える厳密な条件や名称は、必要性に応じて後置または前提章へリンクする。

専門語を使ってよいかは、語感や公式シラバスの用語例だけで決めない。**まず `chapter.yaml` の `prerequisites` と `textbook/dependency-graph.md` を確認し、その概念が前提章で定義・説明済みかを判定する。** 前提章で学習済みの用語は通常教材でも既知として使ってよく、初出箇所では前提章へのリンクを置く。

一方、前提章で未導入の専門語を、数学監査の都合だけで本文の前提語彙にしない。必要なら、(a) その章で意味から導入する、(b) 共通基礎章へ追加して依存関係を明示する、(c) 発展補足へ退避する、のいずれかを選ぶ。

**統計問題を解くために不要な数学・プログラミング側の専門語も主語彙にしない。** たとえば変数変換では「逆像」「像」「枝」から始めず、「`g(x)=y` を満たす元の `x` を全部求める」「元の範囲を変換後の変数の不等式へ直す」と説明する。極座標は `x=r\cos\theta, y=r\sin\theta` と角度範囲を定義すれば足り、`atan2` のようなプログラミング関数名を導入しない。

**本文には、執筆者側の取捨選択を説明するメタコメントを書かない。** 「〜を覚える必要はない」「試験では〜で十分」「本章の目的ではない」「通常教材では〜まででよい」のような文は置かず、不要な事項は単に本文へ出さない。

**問題文の自己完結性も読者粒度の一部とする。** 章頭に分布・記号をまとめて書いたことを理由に、各演習から計算の出発点を消さない。問題だけを切り出しても、確率変数・母数・分布のパラメータ化・新しく定義する統計量・必要な確率密度関数や使用可公式が追える状態を原則とする。詳細は `EXERCISE_GUIDELINES.md` の「問題文の最低記載水準」に従う。

数学監査と読者粒度監査は目的を分離する。数学監査は誤り・仮定漏れ・導出欠落を見つけるが、**監査を通すためだけに通常教材へ一般論を展開しない**。読者粒度監査は「その概念が既習か」「説明順が意味→具体例→一般式になっているか」を見る。

## 2. 1単元1ページ

新規章は `index.md` 1枚を本文の正本とし、導入・定義・定理・例題・演習・詳細解答・本番ドリルを別Markdownへ分離しない。

GitHub Pagesでは `<!-- solution-start -->` と `<!-- solution-end -->` の間を折りたたみ表示する。Markdown自体には通常のMarkdown・KaTeXとして解答を書き、折りたたみのためだけに本文へHTMLを手書きしない。

旧 `00_overview.md`〜`09_past_exam_practice.md` 形式は既存章の移行対象としてのみ扱う。新規章・新規テンプレートでは増やさない。

## 3. 章構成の正本

通常章の見出し構成、導入部の順序、本文の基本的な並び、演習と解答の配置は [`templates/chapter/index.md`](templates/chapter/index.md) に従う。**構成を変更するときは、まずテンプレートを変更し、その後に既存章をテンプレートへ合わせる。style-guide側へ同じ構成を再掲しない。**

F0-00のような数学速習・案内章は通常の統計章と役割が異なるため、通常章テンプレートの例外としてよい。

レビュー済み章を再確認するときは、本文内容だけでなくテンプレートとの差分も確認する。章タイトルだけをH1とし、本文主要節をH2、その下をH3とする。

## 4. 問題レベル

通常教材では次のレベルを使う。

- Level A：5〜10分の単一技能。
- Level B：10〜15分の2〜3小問。
- Level C：20〜30分、4〜6小問の本番標準。
- Level D：30〜45分、理解を深める発展問題。

標準配分は A 20%、B 25%、C 45%、D 10% とする。Level Cは原則として公式過去問の大問より少し短い計算量にする。

解答そのものの粒度、途中式、定理適用、採点基準は `EXERCISE_GUIDELINES.md` に従う。

## 5. 過去問との接続

Level C/Dと30分ドリルは、可能な範囲で一つの設定を複数小問へ連結し、単発技能だけに切り縮めない。

各章の `chapter.yaml` に `past_exam_alignment` を置き、年度・科目・大問ID、テーマ、現在の章で担当する技能、後続技能を記録する。実過去問は問題文・図表を転載せず、公式公開PDFまたは公式問題集を参照させる。

未修単元へ接続する小問は「先取り」または「後続章で再挑戦」と明示する。

## 6. 通常教材固有のメタデータ

各問題には、通常教材の検索・進捗管理に必要な範囲で安定ID、Level、目安時間、主題、使用技術、計算量を付ける。

過去問由来の構造を使う場合は、出典の年度・問題番号、確認元、確度、変更点を記録する。第三者サイトのテーマ一覧は `third_party_topic_index`、公式問題・公式問題集を直接確認した場合だけ `official_problem` とする。

## 7. validation と audit

通常教材の機械検証は次を使う。

```bash
npm run validate
npm run validate:pages
```

粒度・用語の改善候補は次で抽出する。

```bash
npm run audit:textbook-granularity
npm run audit:terminology
```

validationは壊れた数式・リンク・構造など機械的に判定できる問題を扱い、auditは人間の判断を要する改善候補を非ブロッキングで扱う。共通の判定方針は `CONTENT_GUIDELINES.md` に従う。

### 7.1 定理・証明・導出への参照リンク

「前章の○○定理から」「この証明はF0-02Bへ分離した」のように、**別の場所にある特定の定理・補題・証明・導出を論理的依存先として参照する場合、章トップへのリンクだけでは不十分**とする。読者がクリック1回で該当箇所へ着地できるよう、参照先に明示的な安定anchorを置く。

- 定理・補題など単一のformal result：`<a id="thm-..."></a>`
- 複数節にまたがる証明・導出：`<a id="ref-..."></a>`
- 参照側：`[Borel--Cantelli第1補題](../.../index.md#thm-borel-cantelli-1)` のようにfragmentまで書く。

`#` のない章トップリンクは「次章」「関連章」「章全体を読む」のような通常ナビゲーションには使用してよい。一方、「この定理を使う」「証明はここ」「導出はここ」という依存参照には使用しない。

CIでは `npm run validate:formal-references` がsource Markdown上で、formal dependencyの章トップ止まり、存在しないanchor、安定anchorなしの高確度な定理参照を検出する。さらに `npm run validate:pages` では生成後の教材に対して `thm-` / `ref-` fragmentが実在することを確認し、**sourceでは正しく見えてもPages上では飛べない**状態を防ぐ。

### 7.2 定義直後の例は「定義を満たすこと」まで確認する

定義の直後に具体例を置くとき、「$d_1$ も距離です」「$(0,1)$ は開集合です」のように結論だけを書いて例扱いにしない。**その対象が直前の定義の各条件を満たすことを、最低1回は式または論理で確認する。** とくに複数条件からなる定義では、非自明な条件だけを飛ばさない。

`definition-example` 監査は **strict が既定値** である。新規ページや、監査ルール導入後に内容を変更したページは、formal definition ごとに具体例による確認か、定義単位の理由付きskipを持たなければCIを通さない。`<!-- definition-example-audit: strict -->` は後方互換のため認識するが、通常は書く必要がない。

formal definition の具体例は次のマーカーで囲み、対象となる `def-` anchor を列挙する。

```md
<!-- definition-example-start: def-example-01 -->
### 例：具体例

**定義の確認**

1. 定義の条件1を確認する。
2. 定義の条件2を確認する。
3. 非自明な条件は式で確認する。
<!-- definition-example-end -->
```

一つの例で複数の定義を同時に確認する場合は

```md
<!-- definition-example-start: def-example-01, def-example-02 -->
```

のように複数anchorを書いてよい。

直接の具体例を置くこと自体が不自然な定義に限り、

```md
<!-- definition-example-skip: def-example-01 | 具体例を置かない理由をここに書く -->
```

で定義単位に例外化してよい。単に執筆を省略する目的では使わない。

ページ全体をまだ definition-example 監査へ移せない場合だけ、ページ先頭付近に

```md
<!-- definition-example-audit: loose -->
```

を置いて一時的に緩和できる。**loose は例が不要という品質基準ではなく、未監査であることを明示する移行コメント**として扱う。DREAM THEATER の各Batchでは、対象ページを修正するなら原則 loose に逃がさず、そのBatch内で定義例を閉じる。

移行期に限り、PR #88 の導入時点から一度も変更されていない既存ページは grandfather してCIを通す。これらは内容が1文字でも更新されれば既定のstrictへ移る。最終Batchではこの移行例外を撤去し、未監査ページは `loose` コメントがない限り一律にstrictとする。

CIの `npm run validate:definition-examples` は、strict ページについて **全ての formal definition が検証ブロックか理由付きskipで明示的に処理されていること**、検証ブロックに `**定義の確認**` があること、参照anchorが実在することを確認する。これにより、文章の流れだけで具体例を置いて「例あり」と数えてしまう抜け道を防ぐ。数式そのものが正しいかは引き続き数理査読で確認する。
