## 1. 教育目的と中心問い

中心問いは **「プログラムの何をテストで確かめ、何をLean 4で証明し、現実の製品実装との距離をどう埋めるか」** である。Leanを単なる数学の証明記法としてではなく、実行可能な仕様、定理の証明、テストオラクル、他言語製品の差分テストの四者を結び付ける道具として学ぶ。

履修後、学習者は次を自力で再構成・実行できる。

1. Lean 4の純粋関数、代数的データ型、再帰、停止性、依存型を用いて小さな実行可能仕様を定義する。
2. 仕様の不変条件・到達可能性・入出力関係を命題として定義し、構造帰納法・場合分け・書換え等で主要な証明を閉じる。
3. 例示テスト、性質ベーステスト、変異テスト、メタモルフィックテスト、状態遷移テストを区別し、反例の縮小を追跡する。
4. Lean上の実行可能な参照モデルとPython/TypeScriptの独立実装を、同一の入力と出力契約で比較する Differential Testing / Differential Random Testing（DRT）を設計する。
5. CIでLeanの証明検査と製品のランダム差分テストを分離し、失敗入力・シード・バージョンを保存して再現する。
6. **証明された仕様の性質**、**テストした入力での実装との一致**、**まだ保証されていない製品の性質** を証拠ごとに説明する。

学習の主線：

~~~text
仕様で表したい要求
    → Leanで実行可能なモデルを作る
    → モデルについて命題を立てて証明する
    → 例示テスト・性質ベーステストでモデルと仮定を検討する
    → 同じ入力を本番実装とLeanモデルに通す
    → 不一致を縮小・原因分類し、証明と差分テストをCIで継続する
~~~

**境界を明示する。** Leanでモデルの性質を証明しても、そのモデルとPython/TypeScript/Rustの製品コードが全入力で同値とは限らない。DRTは有限個の入力に対する一致検査であり、製品実装の全入力での正しさの証明ではない。さらに、仕様が利用者の意図に適合するかは仕様レビューが必要である。これらの差を教材の最初から最後まで事例と証拠で示す。

- 既存の [AUT/CMP/CPLX計算理論PLAN](../plan_done/DREAM_THEATER_THEORETICAL_COMPUTER_SCIENCE_P_VS_NP_PLAN.md) が形式言語・Turing機械・計算可能性・計算量を所有する。本系列はLean 4による仕様・証明・テスト工学を所有し、P対NPやCook–Levinを再講義しない。

- 数学的帰納法、集合、論理結合子は既習の基礎があれば利用するが、**Leanでの命題と証明の構文、Decidable/Bool、tacticsは初習**として教える。高度な数理論理・圏論・計算量理論を一律必修にしない。
- API/IOの製品実装、pytest、fast-check、CI、JSONを含む開発実務の用語は使用前に講義内で定義する。PythonかTypeScriptの基礎的なプログラミング経験を推奨するが、言語固有のテスト技法は本講義で導入する。

## 5. 各章の制作・証明・実行ゲート

1. **使用前に導入する。** Leanの基本構文、型、命題、到達可能性、テストオラクル等をformal statementやコード例の前で通常文により説明し、後続の既習概念は実在するstable anchorへ使用箇所からリンクする。
2. **数学的証明を読める形で記す。** 前提、型、定義域、再帰の減少、場合分け、帰納仮定、書換えの根拠、存在・一意性、エラー分岐を本文・詳細解答で示す。「Leanが受理した」だけで証明を省略しない。
3. **実際に走るコードを伴う。** Leanツールチェーンと依存を固定し、少なくとも該当モジュールの`lake build`、test driverの`lake test`、外部実装側のテストを実行する。CLIの出力と失敗事例を明示する。古い教材コードをそのまま最新版で実行可能だと仮定しない。
4. **証明を弱めない。** `sorry`、無根拠な`axiom`、不適切な`native_decide`や外部コードへの信頼拡張は検証の代替としない。必要な公理・trusted computing baseと証明未済部分を別途監査する。
5. **モデルの正しさとモデル適合性を分離する。** Leanモデルについての`theorem`、具体例の`#guard`、製品との差分テストの成功を別々に提示する。製品の全入力を証明したと誤記しない。
6. **有効領域と不正領域をテストする。** 前提が強すぎるために命題が空虚になる例、型に入るが到達不能な状態、オラクルの入出力欠陥、エラー枝を講義ごとに必要な分だけ検証する。
7. **全章に演習と詳細解答を付ける。** 原則Level A 4題以上、B 3題以上、C 1題以上を最低線とし、証明・実装・テストそれぞれを学習目標に応じて追加する。演習は紙上の論証だけでなく、走るプログラム／再現可能なテスト入力を含める。
8. **新規章は別観点で再査読する。** 本文・主要証明・全演習と解答の自己査読と、独習者としての説明順・誤解・実行可能性の再読を分離する。第三者独立査読と偽称しない。
9. **公開・CI整合を確認する。** 初回実装時に系列manifest、章メタデータ、knowledge DAG、科目別目次を必要な範囲だけ更新し、変更に応じたchanged-only validationを実施する。共有基盤を変えるときはfull validationへ昇格。コードはブラウザ表示だけでなく実行環境で検証する。
